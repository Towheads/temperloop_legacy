You are running the **sweep** command. Goal: drive every **Ready singleton** on a board — an issue triage marked Ready but left **ungrouped** (it is *neither* a sub-issue of an epic *nor* an epic parent) — from open to merged, in **chunks of up to `$SWEEP_FANOUT_WIDTH` concurrent issues**. This is the singleton-path peer to `/build`: `/build` drains the *epic'd* work (via a plan note); `sweep` drains the *lone* Ready issues. Together they clear the whole Ready pool with no overlap — the "neither a sub-issue of an epic nor an epic parent" filter is the seam between them.

```
                 ┌─ epic'd survivors ─┬─ Foundational ─► /assess --epic N ─► /build
/triage  Ready ──┤                    └─ Operational  ─► /sweep   (SWEEP_ADMIT_OPERATIONAL_EPICS, epic #1847 ("epic-as-metadata for operational work"))
                 └─ singletons ─────────────────────────► /sweep   ◄── you are here
```

The `Foundational` / `Operational` split above the singleton row is the **class-keyed partition**
(`claude/work-class-policy.md`): a triaged epic's own work-class label, not its epic-vs-singleton
shape alone, decides whether its Ready legs need the `/assess`→plan→`/build` ceremony or can join
`sweep`'s chunked pool directly — Step 1 item 6 below is where that admission actually happens.

Because the singletons skip `/assess`, they have **no pre-execution contract-clarification stage**. So `sweep` adds one: **Phase 1**, an upfront question sweep (the singleton path's missing `/assess`-equivalent) that resolves ambiguity *before* any fix worker runs.

## Inputs

- `--board <N>` (optional) — which board's singletons to drain. stageFind = `3` (repo `<org>/stageFind`), foundation = `4` (`<org>/foundation`). Explicit `--board` is **preferred**; if omitted, the board is **inferred from the local repo** (see Step 0.2), consistent with `/triage` and `/assess`. Inference is bounded to the repo you're standing in — it resolves only to that repo's registered board and prints the resolution before acting, so it cannot silently pick an *unintended* board (the prior arbitrary stageFind-`3` default is gone; foundation#547 established that bounded, printed inference is not the silent-board footgun the old default was).
- `--dry-run` (optional) — rehearsal: validate + build the pool + run Phase 1's detection, then **print** the pool + which issues carry open questions, with **zero** mutation (no claim, no worker, no merge, no label/comment writes). See Step 3's dry-run note.
- `--unattended` (optional) — **default posture** (per the batch-unattended convention): after Phase 1's answers are in, Phase 2 runs without further prompts — it auto-merges each green PR at the per-chunk merge pass and **parks** anything that escalates rather than halting. Phase 1 is the one interactive gate; on a truly operator-absent run it leaves all flagged issues parked and drives the clean (un-flagged) set — now chunked, like every run mode (see Step 2). An unattended/headless run **never** uses the tier-2 overlap (#626 — a headless run has no background-completion re-invoke loop): it keeps the tier-1 synchronous chunked path of Step 3 exactly as specified, with no background launch of any kind.

## Operating principles

- **Reuse `build-level.mjs` — do not reimplement the fix loop.** The per-issue mechanics (claim → worktree → isolated worker → acceptance gate → scan → push-by-SHA → PR open → CI poll) already live in the saved Workflow `claude/workflows/build-level.mjs` (foundation #422), which drives a *set* of items and returns a small `{parked, escalations}`. `sweep` invokes it **once per chunk** — a multi-item "level" of up to `$SWEEP_FANOUT_WIDTH` issues, executed through the workflow's own within-level `parallel()` path (the exact machinery `/build` uses daily) — chunk after chunk. No new workflow file; the command is a thin conversational driver over the existing workflow + machinery. See [[Decisions/foundation - build workflow-machinery invocation seam]]. <!-- cite: SW.1 guard:claude/workflows/build-level.mjs -->
- **Per-chunk memory isolation is structural, not aspirational.** Each per-chunk workflow invocation is a **fresh process**, and every fix worker inside it is an isolated `agent({schema})` whose context is **discarded on return** — so nothing bleeds between issues or between chunks, and the conversational orchestrator only ever sees the small `{parked, escalations}` object per chunk (bounded context across the whole sweep). <!-- cite: SW.2 guard:workflows/scripts/build/build.config.sh -->
- **Chunked fanout — parallel within a chunk, synchronous between chunks.** The Phase-2 set drives as **chunked multi-item invocations**: consecutive groups of up to `$SWEEP_FANOUT_WIDTH` issues form one `build-level.mjs` invocation (a multi-item `items[]` array), and each invocation runs **synchronously to completion** before the next chunk launches. Merges batch at chunk boundaries (the per-chunk merge pass), the quota gate runs between chunks, and board WIP rises to at most the chunk width — the same accepted properties `/build` has per level. **`SWEEP_FANOUT_WIDTH=1` is the rollback lever: it restores full legacy behavior — strictly one-issue-at-a-time drive *and* questions-first ordering — as a config-only change, no spec revert needed.** (On every tier-1 arm — width 1, unattended/headless, degraded, or `--dry-run` — Phase 1 always completes before any Phase-2 chunk launches, so questions-first holds; the `=1` guarantee is what keeps that pinned now that tier 2, next bullet, relaxes ordering at width > 1 on attended runs.) The ratified design's **tier 2** — the attended question-overlap tier — is **now part of this spec**: the next bullet defines it; Step 2 owns its launch and the chunked fix loop its composition (`docs/adr/0012-sweep-two-tier-parallel-execution.md`).
- **Tier 2 — attended question-overlap: chunk 1 in the background, a same-run tail chunk.** On an **attended** run, once Phase-1 detection has partitioned the pool into a **clean set** (no open question) and a **flagged set**, the orchestrator launches **chunk 1** — the clean set's *first* chunk, up to `$SWEEP_FANOUT_WIDTH` issues (the width cap holds for it like any chunk) — as a **background Workflow invocation *before* presenting the Phase-1 question batch**: the call returns immediately with a task id, and the operator answers the batch while chunk 1 builds. Issues whose questions the operator answers during the batch accumulate into the **tail chunk** — *definition:* the chunk assembled from the question batch's **answered** issues, driven **in this same run** after the batch resolves, sequenced after any chunk whose merge pass is still pending, and honoring the per-chunk quota gate exactly like every other chunk (an unanswered/deferred issue never joins it — it stays flagged for the next run; answered issues beyond `$SWEEP_FANOUT_WIDTH` split into further width-capped tail chunks). Tier 2 activates **only** when all four hold: **(a)** the run is **attended** (a live operator — never the `--unattended`/headless arm, #626: a headless run has no background-completion re-invoke loop, so the unattended arm keeps the tier-1 synchronous chunked path unchanged); **(b)** `$SWEEP_FANOUT_WIDTH` > 1 (width 1 = full legacy semantics — sequential drive *and* questions-first ordering — tier 2 disabled); **(c)** background Workflow invocation is **available** in the harness; **(d)** the run is **not `--dry-run`** (the rehearsal's zero-mutation guarantee forbids any background launch — the chunked fix loop's dry-run note prints what chunk 1 *would* have been instead). When (c) fails at run time — the background launch is unavailable or refused — emit the **degradation notice** in Step 2's tier-2 block and fall back to the tier-1 synchronous path: never a silent behavior change, never a stall (synchronous fanout is the designed floor, not an improvisation). *Mechanism note (for executors):* the harness **Workflow-tool contract** is the mechanism — a background invocation returns immediately with a **task id**, and the harness delivers a **`<task-notification>` that re-invokes this conversational driver on completion**, where the chunk's merge pass then runs (the chunked fix loop's tier-2 composition). This is **distinct** from `claude/commands/build.md`'s worker-prompt rule "No long-running background work … a backgrounded gate/eval silently dies": that rule concerns a *subagent's* backgrounded shell process inside a headless worker — reaped when the worker yields, with no notification path back to it — not the conversational driver's own Workflow call, which *does* receive the completion notification and resumes. The pre-report terminal-state assertion remains the backstop against a dropped background chunk: every Phase-2 issue must reach exactly one terminal disposition **regardless of which tier drove it**. <!-- cite: SW.3 incident:F#626 -->
- **The designed floor needs a floor of its own — an unavailable or refused chunk invocation is a named disposition, never a stall.** Tier 2 degrades *to* tier 1, so tier 1 cannot degrade to "improvise": every `Workflow` invocation this command makes is covered by two run-scoped facts. **Step 0.7's preflight** resolves foreground availability *once*, up front, with the remedy named — never rediscovered N chunks deep. **Step 3's refused-invocation disposition** lands every issue of a refused chunk on the existing `parked` terminal disposition with a legible reason and continues to the next chunk, so one refusal never aborts the run and Step 3.5's assertion stays both meaningful and reachable. **Scope this as defensive, not as a fix for an observed foreground stall:** the live 2026-08-02 refusal (temperloop#1048) hit the **tier-2 background launch**, which degraded exactly as its own block specifies; the foreground chunk invocation in the same session was permitted. <!-- cite: SW.13 incident:K#1048 -->
- **Shared-hotspot / composition-root awareness.** When consecutive singletons touch the same file — the canonical example is a composition root (e.g. `AppComposition.swift` / `SettingsView.swift` in a mobile app), but any file that registers/wires up components plays the same role — N's merge can land while N+1 is mid-build, leaving N+1's worktree on a stale base. The pre-PR-open rebase (the `pr.sh rebase` step at `/build`'s 3f push/PR-open boundary, #525) surfaces this conflict deterministically as a `rebase-conflict` escalation rather than a post-PR-open CONFLICTING dead-poll. When partitioning the Phase-2 set into chunks (Step 3), **sequence hotspot-touching singletons deliberately — never into the same chunk**: if two or more Ready issues are known to touch the same shared file, keep the highest-priority one in its natural chunk and defer the others into a **later chunk** — a deferred sibling then rebases cleanly onto the earlier one's already-merged result at its own chunk's pre-PR-open rebase. Two same-file siblings that do end up concurrent surface as a deterministic `rebase-conflict` park, never a corrupt merge — the heuristic reduces parks; the rebase is the correctness backstop. **`CHANGELOG.md` is deliberately NOT one of these hotspots — that is a resolved concern, not a missing case.** It used to be the one file *every* contract-surface kernel item touched, so a multi-item kernel chunk collided on it by construction rather than by coincidence (temperloop#1218). The fix was made at the source rather than in this heuristic: a contract-surface PR now writes its own new `changelog.d/<slug>.<category>.md` fragment — a distinct new path — and `CHANGELOG.md` is rewritten only at the release cut (temperloop#1321 added the fragment directory and its assembler; temperloop#1322 cut the gate over to *requiring* a fragment). Two singletons in one chunk therefore share no changelog line and cannot collide on one, so the chunker needs no CHANGELOG-specific rule and re-adding one would be dead weight. The release cut *does* rewrite `CHANGELOG.md`, but `VERSIONING.md` mandates the cut be one deliberate maintainer PR and `/sweep` only ever drives the Ready singleton pool — a cut never enters a chunk. <!-- cite: SW.5 incident:F#525 -->
- **Park-on-question, no modal halt.** When an issue's worker returns a question (a `blocked` / `design-fork` / `failed` escalation), `sweep` does **not** halt the run or open a conversational round-trip (the `/build` 3d-esc behavior). It **parks** the issue on the board — moves it back to `Ready` (out of In Progress), adds the `needs-clarification` label + the question as a comment, and **assigns the operator** (routing it into their assigned-to-me queue at source, foundation #684) — and **advances**, disposing the rest of the chunk and then the remaining chunks. The `needs-clarification` **label** is the open-question gate (there is no `Blocked` Status bucket — it was retired in #435; an open *question* is a label, just as a dependency block is a native `blocked_by` edge). Parked issues re-enter the **next run's Phase 1** automatically — the label, not a status, carries the question across runs, so the loop self-heals. <!-- cite: SW.4 incident:F#684 -->
- **Claim-first, per chunk — a multi-claim window, claims held until Done.** The board is a cross-session lock. Each of a chunk's issues is **claimed In Progress as the first per-item action** (the workflow's own claim-first step, before its worker investigates), so a driving chunk holds up to `$SWEEP_FANOUT_WIDTH` claims at once — **WIP = the chunk width**, and a chunk is exactly the kernel's documented **multi-claim window** (K#275). Claims are **held until Done**: an issue's board half leaves In Progress on merge/close — no cascade automation exists on this backend, but the closed state alone makes the item read Done immediately (`issue_item` checks `state == closed` before any label) — or via the park path's explicit status move, never a mid-flight release. Consequently `release.sh`'s one-marker-per-window design means it correctly **refuses** to clear a non-latest claim marker — that refusal is **expected and non-fatal** (the marker clear is best-effort; see the Phase-2 park path). Phase 1's read pass is shallow triage-style detection (like `/triage` reading Backlog or `/next` reading Ready) and does not claim — only Phase 2's chunk loop claims.
- **The conversational/workflow split (mirrors `/build`'s default Workflow path).** The **workflow** owns each chunk's 3a–3g and returns `{parked, escalations}` — it never merges, never writes outside its return. **This command (conversational)** owns: Phase 1 (`AskUserQuestion` cannot run inside a workflow), the **per-chunk merge pass**, the **park-on-question** board writes, and the report.
- **The `needs-clarification` label is the open-question marker.** `/triage` drops it (with a `needs-clarification: <question>` comment) on underspecified survivors at source; `sweep` Phase 1 consumes and clears it; park-on-question re-adds it. It is also consumed by `/assess` on the epic path, and — on an autonomous board — **drained by the pipeline** when the operator answers + unassigns (the label is cleared so the item drives again; foundation #657). A plain GitHub label (advisory, mirrors `spike`).
- **Board-native only.** This command requires the board adapter + a registered board (the Step 0 probe). With no board it stops — there is no boardless mode (the singleton pool *is* a board query).
- **Live candidate tagging provenance (temperloop#1257, epic #1225 "model comparison harness") adds no new selection mechanism.** An operator points the existing `$SWEEP_WORKER_MODEL` setting (Step 0.4) at a candidate exactly as they would to change the default tier — that is the *only* lever, and `workflows/scripts/model-comparison/tagging.sh` has no `--model` flag of its own to disagree with it. What live tagging adds is provenance: `tag` (Step 3's per-chunk merge pass, `pr` is set) records a bounded, run-scoped window entry, emits a matching attribution-only telemetry tag through the existing `emit-model-usage.sh` raw lake (temperloop#1253/#1255 — reused, never a parallel stream), and stamps the merging PR's body with model+provider (never a key, never content) **before** it merges. `tagging.sh crosscheck` is the mechanical proof a reviewer or auditor can run later: it fails loudly if a PR's stamp and its recorded provenance ever disagree. Designation is governed by the same committed provider allowlist (`workflows/scripts/model-comparison/allowlist.sh`) every other provider check in this module reads — an unlisted provider is refused, silently skipping the stamp/tag rather than blocking the merge (see Step 3). This is **distinct** from Step 3.6's `emit-command-run.sh` record (`--command sweep`, the whole-run tally) — the two streams answer different questions (which model produced *this PR* vs. how many issues *this run* processed) and both fire on a live-tagged run with no conflict.

   **Call-failure handling — an error is never the permissive branch.** `board_blocked_by_open` is a live network call than can itself ERROR (non-zero exit), not only return empty. An errored call is **not** equivalent to "genuinely no open blockers" — collapsing the two would silently re-admit the permissive read and reopen #1835 through this exact path. **That distinction is only reachable if the call can actually signal failure, and by default it cannot**: `board_blocked_by_open` is a pipe — `_board_gh api … 2>/dev/null | _board_sanitize_control_chars | jq -r …` — and `board.sh` sets `pipefail` nowhere, so a failing `_board_gh api` stage still exits the pipeline via `jq`'s own `0`, with empty stdout: byte-identical to "genuinely no open blockers." **Run the Step-1 blocked_by read in a bash block with `set -o pipefail` enabled *before* sourcing/calling `board.sh`** — `pipefail` is a shell option of the invoking shell, so a pipeline inside a sourced function still honors it once set, and a failing `gh api` stage then surfaces as the function's own non-zero return — and call it in the discriminating shape:
   ```
   if ! open=$(board_blocked_by_open "$BOARD" <issue#>); then
     # cannot establish — conservatively defer, record read-failure
   fi
   ```
   On an errored `board_blocked_by_open` call for an item — i.e. the `if !` branch above fires — treat that item as **"cannot establish — conservatively defer"**: it is deferred this run exactly as if it carried an unresolved blocker (record it for the Step-4 report, distinctly noted as a read failure, not an open-blocker count), never treated as unblocked.

   **The un-defer predicate is explicit and mechanized** — never a live-network guess made ad hoc. A blocker un-defers its dependents **iff its issue is CLOSED AND its landing commit is an ancestor of `origin/<default>`**. Resolve issue→SHA via the blocker's **linked merged PR** — `gh pr list --search "Closes #<n>" --state merged --json number,mergeCommitOid -R "$repo"` — then confirm ancestry with `workflows/scripts/build/worktree.sh deps-merged "$repoRoot" <sha[,sha…]>` (`DEPS_MERGED` = ancestor confirmed, i.e. the depended-on PR has actually landed — the same gate `/build`'s `dependsOn` precondition already uses, reused here rather than reimplemented). **Ambiguity case:** a blocker closed with **no** linked merged PR (closed-as-not-planned, or closed by hand with no PR) **releases its dependents** — there is no merge commit to wait on, and holding a dependent hostage to a PR that will never exist would stall it forever. That "no linked merged PR" reading is only valid when the `gh pr list --search` call **succeeded** and genuinely returned zero rows — **the same call ERRORING (non-zero exit) is a distinct outcome and must NOT be read as "no linked merged PR"**: pass it into `sweep-blocked-undefer.sh` as `linked_prs_query_error: true` (never as an empty `linked_merged_prs` array, which the script treats as the release-eligible ambiguity case) so the script itself conservatively defers rather than conflating "query succeeded, empty" with "query failed". **A blocker whose own sweep disposition — this same run, when the blocker is itself a pool member being driven concurrently — is `parked` never releases its dependents**: parked is terminal-by-disposition with the blocker's work unlanded, so this overrides even a closed+merged read (a park path never actually leaves the blocking issue closed, but the check states this explicitly rather than relying on that incidentally). The deterministic combinator implementing every branch above — each independently fixture-tested — is `workflows/scripts/build/sweep-blocked-undefer.sh` (its own header is the single statement of the predicate; this bullet is a pointer, not a second spec). **Re-checked at chunk boundaries** (Step 3): a blocker open at Step-1 pool-build time can land mid-run, in an earlier chunk of this SAME run, so the predicate is re-evaluated immediately before a still-deferred item would otherwise join a later chunk — never staled to the Step-1 read.

   **Durable frontier marker, for the Step-4 multi-run-stall note.** On a deferral this bullet produces, **sort the open-blocker issue numbers ascending** before both rendering and comparing — `board_blocked_by_open`'s returned order is not guaranteed stable, and the set is what's semantically distinct, not the order it was read in; an unsorted comparison would treat a stable blocker set as "changed" on nothing but a reordering and post a spurious duplicate. Using that sorted list, check the item's already-fetched comments for an existing `Blocked by sweep (blocked_by): <blocker list>` comment naming the **exact same, identically-sorted** open-blocker set. If none matches (first time this exact blocker set has parked this item, or the blocker set changed since the last one), post `gh issue comment <n> -R "$repo" --body "Blocked by sweep (blocked_by): open blocker(s) <#B1, #B2, …>. Deferred this run; re-checked automatically next run."` with `<#B1, #B2, …>` rendered in that same ascending sort — a comment per **distinct blocker-set state**, not per run, so a stall spanning many runs against the *same* blockers (regardless of the read order they arrive in) posts exactly once and never spams the issue. Step 4's multi-run-stall note reads this trail: if the item's comments already carry a `Blocked by sweep (blocked_by):` marker whose timestamp **predates this run** (posted by an earlier invocation, whether or not this run added a fresh one), the item was already blocked as of a prior run — flag it as a **multi-run stall** and name the earliest such marker's date as how long it has stood.
5. **Pool-level cycle walk (temperloop#1835).** The node/edge set for this walk is the **candidate pool as established by items 1–3, plus any members item 6 admits** (item 6 runs and folds admitted members in before this walk executes — see item 6's own ordering note) — the same set item 4 evaluates — **never** the narrower set of survivors remaining after item 4's own drops. This distinction matters: a pool-internal blocker is, by construction, still OPEN at read time (item 4 has not yet un-deferred anything within a single Step-1 pass), so restricting the walk to item 4's post-drop survivors would make it a **permanent silent no-op** — every pool-internal blocked_by edge would already be gone before the walk ever ran. Restrict that candidate set's `blocked_by` edges to pairs where **both** ends are themselves members of that same candidate set (an edge to an item outside the candidate set is item 4's ordinary per-item deferral above, not a cycle concern) and walk the resulting graph with `workflows/scripts/build/sweep-pool-cycle-detect.sh` — standard Kahn's-algorithm topological removal; see its own header for the exact algorithm and the deliberate choice to also catch an item transitively blocked behind a cycle, not only a cycle's direct members. Left unwalked, a genuine cycle (A `blocked_by` B `blocked_by` C `blocked_by` A) would defer every member **forever, silently**, indistinguishable run over run from an ordinary slow-moving single blocker. ## Step 2 — Phase 1: the upfront question sweep (the one interactive gate)

A pooled issue **has an open question** iff it **carries `needs-clarification`** (triage-flagged or parked by a prior run) **OR** your own read of it judges it **underspecified** — the fix can't start because the intended behavior, the choice between two designs, or a missing decision is genuinely ambiguous (not merely a fact a worker could look up). When *you* judge an unflagged issue underspecified, **comment the question FIRST, then label+assign** (`gh issue comment <n> -R "$repo" --body "needs-clarification: <the question>"$'\n\n'"Once answered: on the autonomous pipeline board, unassign yourself to release it straight back to the driver; on other boards leave it as-is — the next /sweep or /assess clears the label. Either way your answer is consumed."`, and only after it succeeds `gh issue edit <n> -R "$repo" --add-label needs-clarification --add-assignee @me`), so the question is durably captured **before** the "handled" markers land and the issue is routed to the operator's assigned-to-me queue at source like a triage flag (the pipeline router then merely parks it, never re-derives/re-posts the question the way the retired `route-needs-input` did — foundation #684; if the comment call fails, do not label/assign — leave it un-flagged to re-enter the next run). **Under `--dry-run` this detection is read-only** — identify and *print* which issues carry or raise questions, but make **no** comment/`--add-label`/`--add-assignee` write and **no** `AskUserQuestion` (the dry-run's zero-mutation guarantee — see Step 3).

**Answered, not underspecified — the comment-anchored exclusion.** Before either arm above raises a question for a pooled issue, check its comments (pulled by Step 1's fetch) against the issue's most recent **flagging-type** comment — either a `needs-clarification: <question>` comment (triage's, per triage.md, or a self-judged flag posted by this section) or a `Parked by sweep — <question>` comment (the Phase-2 escalation-park path, Step 3 below). If a `Clarified (…)` comment (e.g. `Clarified (sweep): <answer>`, `Clarified (triage): <answer>`) postdates that most recent flagging-type comment, the issue is **answered, not underspecified**: it carries no open question. This holds for **both** detection arms — the self-judged-underspecified arm and the already-`needs-clarification`-labelled carrier arm — so a stale surviving label alone does not re-raise an already-answered question, and your own read must not independently re-flag it either. Exclude it from the question batch below and from the detection fanout's `underspecified?` verdict.

**Run the underspecification detection as a parallel subagent fanout.** Partition the pooled issues among concurrent **read-only** subagents dispatched in a single message (one slice per subagent; the already-flagged `needs-clarification` carriers need no re-judging for underspecification — they are question-carriers by definition, only their recorded question is gathered — but DO need the answered-exclusion check above applied, since their comments may already carry a later `Clarified (…)` answer). **Each slice's dispatch prompt MUST name which of its issues are admitted epic members (escalation round 2, HIGH finding).** "Admitted epic member" is ephemeral run-state computed by item 6 above, in this same run — it is not recoverable from an issue's own title/body/labels/comments, and a subagent sees only what its dispatch message hands it. **If a chunk's invocation is REFUSED or unavailable (defensive — the tier-1 floor's own floor).** The call can be denied at invocation time by the harness permission classifier (`Permission for this action was denied by the … auto mode classifier`) even after Step 0.7's preflight passed — the preflight proves the tool and the script are *present*, never that a given call will be *permitted*. A refusal is **not** a `{parked, escalations}` return and **not** an escalation; it is **no return at all**, so with no specified disposition the run stalls or improvises and Step 3.5 then hard-fails on N unchecked entries whose only defect was that the driver was never allowed to start them. **Never retry the refused call** — the same rule `/build`'s classifier-denial recovery states (`claude/commands/build.md` Operating principles): a retry burns cycles and risks denial escalation. 1. **Machinery-park every issue in the refused chunk.** They were never claimed (the claim is the workflow's own 3a step, which never ran), so there is no status to move back, no marker to release, and no worktree to remove — the park is the **durable record only**: `gh issue comment <N> -R "$repo" --body "Not driven by sweep — this chunk's build invocation was refused or unavailable (<the refusal text>). No work was started and nothing was claimed; the issue re-enters the next /sweep run's pool automatically. Remedy: <Step 0.7's remedy line>."` Best-effort: a failed comment warns and continues, and never blocks the disposition (unlike the escalation park, whose comment gates the label, there is no marker here that could outlive a missing question).
2. **Do NOT add `needs-clarification` and do NOT assign the operator.** There is no question to answer. Flagging would inject N spurious questions into the next run's Phase 1 batch and hold the issues out of the drivable pool for a machinery defect that is not theirs — the opposite of the self-healing loop the label exists for. Leaving them clean `Ready` singletons is what re-enters them automatically once the capability is restored.

4. **Continue to the next chunk.** One refusal never aborts the remaining chunks.
5. **Bound the prompt storm — the SECOND CONSECUTIVE refusal ends the attempt loop.** On it, treat the capability as absent for the rest of the run: machinery-park every issue in every remaining chunk per steps 1–3 **without invoking**, and skip the inter-chunk quota gate (nothing is being driven, so there is nothing left to protect). Two attempts is the **structural** minimum evidence separating a one-off refusal from a standing capability absence — the first attempt must happen (step 4 requires it), and the second is what proves it was not a one-off. It is definitional, not a tunable, so it is deliberately **not** a setting; this is what keeps a 9-chunk run from re-prompting nine times. A successful chunk resets the count to zero.

**FIRST, before any merge in this pass: settle every host-config deferral parent-side (temperloop#1182).** `build-level.mjs` embeds its host-config deferral contract in **every** worker prompt, ungated — the worktree-is-populated-from-the-index fact holds on `/sweep` exactly as it does on `/build` — so a sweep worker can return an acceptance entry carrying `passed: false` **plus** `deferred_host_config`, and the shared `isHostConfigDeferral()` exclusion lets that item **park instead of escalate** here too. Such an item's parked record then carries **`host_config_deferrals: [{criterion, host_config}, …]`**, and those criteria are **UNVERIFIED, not passed**. `/sweep` has no §4a, so this is that seat: **you** are the actor that can settle them — this driver runs in `$repoRoot`, the real checkout, which *does* carry the gitignored file the worktree structurally could not. For each entry, before the `pr`-is-set arm below runs:

- **Run the criterion's own check in `$repoRoot`** — never the item's worktree, and **never** by copying the named `host_config` file into one (that is the secret-in-worktree exposure `/assess` A.8 exists to prevent, and it is not an option here at any urgency). And **never** by re-driving the issue: a re-drive lands in a worktree again and reproduces the identical uninformative reading. `/build` §4a owns the full disposition contract (which check counts, and the confirmed-set bar a bare presence probe does *not* meet) — follow it there rather than re-deriving it here.
- **Confirmed** → the criterion is met; proceed to the `pr`-is-set arm and merge exactly as normal. Note the parent-side confirmation (file/env var) in the report's per-issue detail.
- **Not confirmed** (genuinely unset on this host) **or cannot establish** (the check errored, or this checkout is not the host the criterion is about) → **do NOT merge.** The acceptance really is unmet or unknown, and an unattended sweep has no operator seat to widen it — so take the **existing escalation park** treatment below verbatim (its six steps: worktree remove → comment → label+assign → release → record), with the question naming the exact **file / env var the operator must populate** and which arm fired. Record the terminal disposition **parked**. This adds **no fourth disposition** — Step 3.5's three-way `merged` / `resolved (verdict)` / `parked` partition and the telemetry emitter's `merged + resolved + parked == items_processed` arithmetic close unchanged.

None of this relaxes the `/assess` A.8 confirmed-set bar; it moves **who** confirms, never **whether**. An item with no `host_config_deferrals` field skips this entirely — the common case, and a no-op on every ordinary sweep run.

**SECOND, before any merge in this pass: regime selection for member-bearing chunks (temperloop#1847 follow-on, preserving the kernel merge-autonomy contract).** `claude/CLAUDE.md § Merge autonomy & consent` states the invariant plainly: "only a clean, disjoint set is timed; a risky set is always modal." Every ordinary sweep chunk is a set of unrelated Ready **singletons** — independent by construction, which is why the merge arm below has always landed each green PR immediately with **no risk check at all**; that stays true for a singleton-only chunk, byte-identically, after this item. An **epic-admitted member** (Step 1 item 6, `$SWEEP_ADMIT_OPERATIONAL_EPICS`) breaks that independence assumption: two legs of the same epic are drawn from one design and are far more likely to touch the same files or interact than two unrelated singletons, so a chunk that mixes them is no longer provably independent just because they landed together. **This is the one place in Step 2/3 where an admitted member's provenance is deliberately NOT "indistinguishable from a singleton"** (contrast Step 1 item 6's own framing for chunking/`blocked_by`/questions) — merge risk is exactly the concern admission introduces, so the merge pass is where it has to be checked. Carry each pooled issue's Step-1 admission route (item 1 singleton vs. item 6 epic-admitted) forward as a per-issue flag through Step 2/3 bookkeeping — no new `build-level.mjs`/Workflow field is needed, since this is orchestrator-only accounting the workflow never branches on.

**What becomes of a sweep-originated preservation ref.** A parked sweep item is **re-driven fresh** on a later run — resume is a re-run from the issue, not an in-place continuation — so `/sweep` never calls `worktree.sh restore` and the preserved commit never reaches `origin/<default>`. `prune`'s **ancestry** gate (the preserved commit is an ancestor of the merged tip) therefore *structurally cannot fire* for a ref this path minted; the **disposition** gate is the one that reaps it, when the originating issue reaches a terminal (CLOSED) state. That is what the issue-number suffix on the slug is for (this Step 3's `items[].slug` rule, above): `worktree.sh prune` parses the trailing `-<N>` back out of the ref name to look the issue up. While the issue is still open the ref is *reported* (`PARKED_REF`) and held, never reaped — so the abandoned attempt stays recoverable, on that host, for exactly as long as the question it parked on goes unanswered. `/sweep` itself never deletes a preservation ref.

**Tier-2 composition (attended overlap runs only).** When Step 2 launched chunk 1 in the background, sequence Phase 2 as follows once the question batch resolves:

1. **Wait — bounded, never indefinitely — for chunk 1's completion `<task-notification>`** (it re-invokes this driver with chunk 1's `{parked, escalations}`). Do not launch any other chunk while a chunk's merge pass is pending. *Notification timing is turn-boundary semantics:* the harness delivers a task notification when the current turn ends, never literally mid-call — so a notification that arrived while the question batch was still open is processed immediately after the batch resolves, and chunk 1's merge pass runs right then. **The bound:** if, once the batch has resolved, chunk 1's notification has *not* arrived, poll the chunk's recorded task id's state on the same background-`sleep` wake pattern the per-chunk quota gate uses — launch a background `sleep $SWEEP_BG_POLL_INTERVAL` (`run_in_background: true`), on each wake check the task's state/output, and repeat up to `$SWEEP_BG_POLL_ATTEMPTS` polls total (both settings sourced in Step 0.4; `${SWEEP_BG_POLL_ATTEMPTS:-6}` / `${SWEEP_BG_POLL_INTERVAL:-120}` on a non-vendoring checkout). A poll that finds the chunk complete recovers its `{parked, escalations}` from the task output and proceeds to the merge pass exactly as if the notification had arrived. **On exhaustion, treat chunk 1 as a dropped-background escalation:** log one line (`tier-2 chunk 1 unaccounted after $SWEEP_BG_POLL_ATTEMPTS × $SWEEP_BG_POLL_INTERVAL s — treating as dropped background chunk`), annotate each of chunk 1's checklist entries `unresolved-escalated (dropped background chunk)` **without checking them** — the annotation is a diagnostic, deliberately NOT one of the three terminal dispositions — and proceed directly to Step 3.5, whose terminal-state assertion then hard-fails loudly on the unaccounted entries per its existing contract. **The Step-3.5 assertion is REACHABLE in exactly this failure case** — the bounded wait is what guarantees the driver arrives at it instead of blocking forever on a notification that will never come; an unbounded wait would make the claimed backstop unreachable.
2. Run **chunk 1's merge pass** exactly as above (it is a chunk like any other — merge the green PRs, close the verdict-only spikes, park the escalations), then the per-chunk **quota gate**.
3. Drive the **remaining clean chunks** synchronously through the loop above, gate between each.
4. Drive the **tail chunk** (the batch's answered issues) **last** — in this same run, sequenced after every chunk whose merge pass is still pending, and behind the same per-chunk quota gate as every other chunk.

Skip the gate after the **last** chunk (nothing left to protect → fall through to Step 4).

**`--dry-run`:** STOP before Phase 2's first invocation. Print the singleton pool, which issues carry open questions (Phase-1 detection only — no `AskUserQuestion`, no label writes), and the Phase-2 set that *would* be driven **plus its chunk partition** (chunk width `$SWEEP_FANOUT_WIDTH`, hotspot deferrals called out). On a run where tier 2 *would* activate (attended, width > 1, background invocation available), additionally print which issues **would form chunk 1** (the background overlap launch) and which **would go to the question batch** — but launch **nothing**: `--dry-run` stays zero-mutation, so no background invocation is ever made under it. End with "Re-run without `--dry-run` to execute." Zero mutation.

## Step 3.5 — Pre-report terminal-state assertion

Before emitting the Step-4 report, assert that **every entry in the Phase-2 TaskCreate checklist is checked** (has a recorded terminal disposition) — **every Phase-2 issue across all chunks**, since the checklist was minted flat over the whole set before partitioning, an issue lost at a chunk boundary (dropped from a chunk's `items[]`, or left undisposed by a per-chunk merge pass) fails this assertion exactly as a skipped issue did in the sequential shape — and that includes a tier-2 **background chunk 1 whose completion notification never arrived or was dropped**: its issues are checklist-tracked identically, so a lost background chunk surfaces here as unchecked entries rather than silently vanishing (the assertion is the tier-agnostic backstop the overlap tier leans on — reachable in that failure case precisely because the tier-2 wait on the notification is **bounded**, Step 3's composition item 1, never an indefinite block). A **refused or unavailable chunk invocation** is covered by construction rather than by a branch here: Step 3's refused-invocation disposition lands each of that chunk's issues on the existing `parked` disposition, so the assertion stays **meaningful** (it is not satisfied by a fourth escape-hatch disposition invented for machinery failures) and **reachable** (that disposition is taken synchronously at the refusal — there is no notification to wait on, so nothing to bound). Specifically: <!-- cite: SW.9 class:false-complete-report -->

1. For each checklist entry, confirm it carries one of: `merged`, `resolved (verdict)`, or `parked`.
2. **Any unchecked entry is a hard error** — do NOT emit the Step-4 report. Instead, surface loudly:

   > **SWEEP ABORT — terminal-state assertion failed.**
   > The following Phase-2 issue(s) have no recorded terminal disposition: #N `<title>`, …
   > This indicates a bug in the sweep loop (an issue was silently skipped). Investigate before re-running.

   Stop. Do not attempt partial-report output. The hard stop makes a silent skip visible immediately rather than propagating a false-complete signal downstream to the board or operator.

This assertion is the structural guarantee that makes silent skips impossible: the TaskCreate checklist is the worklist-lock; the pre-report check is the key.

## Step 3.6 — Epic-closing gate, then emit the run telemetry record

### A. Epic-closing gate (end-of-run, this run's review population)

Once Step 3.5's assertion passes, `/sweep` reviews **this run's review population** (built below) and decides, per epic, whether its parent is offered for close, reported as progress, or reported only. Running this review exactly once at the end of every sweep run is **mandatory** — a run whose population is empty still runs it and records the genuine zero, it never skips the step outright, because a skipped review and a review that found nothing to do are indistinguishable from outside unless the run itself says which happened.

**Build this run's review population — persistent, not one-shot (round 5 fix, escalation HIGH finding).** A fully-drained epic has ZERO Ready legs left (every one already merged/resolved), so Step 1 item 6 can never re-admit it once it's fully drained — a population built from item 6's admissions alone would never see that epic again, making every "re-offered next run" / "re-checked next run" promise below structurally dead. The population is instead the **union of two sets**, queried/assembled once per run:

- **(a) This run's item-6 admissions** — every Operational epic Step 1 item 6 admitted this run (grouped once per epic, the SAME grouping item 6 already computed — never re-derived). Unconditional membership: an epic item 6 already vetted and admitted needs no further read to belong here.
- **(b) The admission-eligible set** — every still-**open** Operational-epic parent carrying triage's `<!-- triage:edges-considered -->` marker, **independent of whether any of its legs was Ready this run**. Query the board **once**: `board_item_list "$BOARD"` (or, absent the setting, skip this arm entirely — see below), filter to items whose `.labels` contains `Operational` **and** that have at least one native sub-issue (`board_sub_issues "$BOARD" <n>` non-empty — the same structural parent check item 1 already uses, confirming this is a real epic parent and not a bare Operational-labeled issue); for each such candidate, pull the edges-considered marker the same way item 6 already does (`gh issue view --json comments`, checking for `<!-- triage:edges-considered -->`). **`epic_open` is true for every candidate this query returns** — `board_item_list` is documented as the board's ACTIVE (open) slice (`workflows/scripts/board/lib/board.sh`), so this arm never needs a separate open/closed read; naming that reliance here explicitly means a future query-mechanism change can't silently default the field to false and regress the round-5 persistent population. A read failure for any candidate (the label read, the sub-issues read, or the marker read) sets `reads_available: false` for that candidate — an error is never the permissive branch, so an unread candidate simply doesn't enter the population via this arm this run (it can still enter via arm (a), or via arm (b) on a later run once the read succeeds).
- **This arm runs only when `$SWEEP_ADMIT_OPERATIONAL_EPICS` is `1`** — with the setting off, arm (b) is skipped entirely (no query, no reads), matching item 6's own unconditional skip; the population is then arm (a) alone, which is always empty (item 6 never runs), preserving the zero-epic fast path's rollback identity exactly.
- **Feed the combinator** — `{epic: E, admitted_this_run, reads_available, epic_open, has_sub_issues, epic_label_operational, edges_considered_marker}` piped to `workflows/scripts/build/sweep-epic-review-population.sh` (deterministic, no network; see its own header for the exact precedence — admitted-this-run wins unconditionally, then a read-failure refusal, then not-open/not-a-parent/not-operational/marker-missing, then admission-eligible). This run's review population = every epic for which the combinator returns `in_review_population: true`.

This union is what makes the declined-offer re-offer, the cannot-establish re-check, and the pending-decisions dedup-across-history (§ item 4's `left-open-unattended` branch below) genuinely live: a fully-drained epic re-detected by arm (b) every subsequent run must not re-append a pending-decision entry, which is exactly what that dedup check guards.

**Zero-epic fast path.** A run whose review population (arms (a) and (b) combined) is empty — the setting off, or on but neither arm found anything — sets `epics_reviewed=0`, `epics_closed=0`, `epics_left_open=0` and proceeds straight to Subsection B with those three zeros — no per-epic reads, no writes.

**Provision the `keep-open` label idempotently, once per run, before the per-epic loop below** — `_board_issues_ensure_label "$repo" "keep-open" "d4c5f9"` (in scope from `$BOARD_LIB`; its inner `gh label create` is `|| true`, so a re-run against a repo that already carries the label is a harmless no-op — the same probe-and-create idiom `build.md`'s retro-tracker mint and `capture.sh`'s work-class labels already use). Run this call once, before evaluating the first epic in the population — never per epic.

Then, for **each distinct epic `#E` in this run's review population**:

1. **Establish `#E`'s member list, then re-pull every member's CURRENT state.** Call `board_sub_issues "$BOARD" <E>` fresh here, at the top of this per-epic loop, **regardless of which arm admitted `#E`** into this run's review population — an arm-(a) epic's member list was already enumerated by item 6's own per-epic reads, but an arm-(b) epic (the round-5 persistent-population case) never passed through item 6, so no such snapshot exists for it there; one fresh call covers both uniformly, so nothing downstream in this item needs to know which arm admitted `#E`. **A `board_sub_issues` call that ERRORS is handled OUTSIDE the combinator, never by feeding it an empty `members: []`:** every epic admitted into the review population is structurally guaranteed at least one native sub-issue (arm (a)'s admission implies a Ready leg existed; arm (b)'s own query already required `board_sub_issues` non-empty), so a genuinely-empty result from a call that SUCCEEDED can never happen here — `total_members == 0` is unreachable once this call runs. An ERRORED call is therefore the only way this item could ever produce zero members, and that case skips the combinator (§ item 3) entirely for `#E` and routes straight to item 4's `cannot-establish` branch, `reason: member-reads-unavailable` — the same outcome `member_reads_available: false` would produce, without ever risking the combinator's `total_members == 0` precedence (§ its own header) winning first and silently dropping the epic from the report as `no-members`. Once the call succeeds, for each member `<m>` it returns: `gh issue view <m> -R "$repo" --json state`. `gh` returns this field **UPPERCASE**; a member's state is `"CLOSED"` (reached via a merged PR or a spike verdict-close — **a `parked` member is never terminal for closing-gate purposes and, by construction, never reaches `state == "CLOSED"`**: the park path moves the issue back to `Ready` and never closes it) or `"OPEN"` (anything else). Pass the `state` value straight through to the combinator (§ item 3 below) **unmodified** — it matches this exact uppercase casing natively, the same convention `sweep-blocked-undefer.sh`'s input schema already documents; do not lowercase it. A read that ERRORS for any member sets `member_reads_available: false` for the whole epic — an error is never the permissive branch, the same discipline item 4's `blocked_by` read and item 6's per-epic reads already apply.
2. **Read `#E`'s own labels, assignees, comments, and author** — one call, `gh issue view <E> -R "$repo" --json labels,assignees,comments,author`. `keep_open_label_present` = true iff `keep-open` is among the labels. A read error sets `labels_read_available: false`.
3. **Feed the combinator** — never invoked at all for an epic item 1 already routed straight to `cannot-establish` on a `board_sub_issues` call error; otherwise `{epic: E, member_reads_available, labels_read_available, keep_open_label_present, attended, members: [{issue,state}, …]}` piped to `workflows/scripts/build/sweep-epic-closing-gate.sh` (deterministic, no network; see its own header for the exact precedence — total-members-zero, then either read-failure, then keep-open, then fully-drained branching on `attended`, then partial, then no-progress). `attended` is this run's own attended/unattended posture (Step 0's `--unattended` flag), the identical signal every other attended/unattended branch in this doc already reads.
4. **Act on the verdict:**
   - **`cannot-establish`** (a member or label read failed, OR item 1 routed `#E` here directly on a `board_sub_issues` call error, bypassing the combinator entirely) → report only (§ Step 4), naming the epic and which read failed. Never close, never write a pending-decision entry — the run cannot establish drain state, so it asserts nothing stronger than that.
   - **`keep-open`** → report only (§ Step 4), naming who to ask: `assignees[0].login` if present, else the most recent comment's author, else `author.login`. **Never** offered for close, and no board write of any kind.
   - **`offer-close`** (fully drained, attended) → batch every such epic this run into one `AskUserQuestion` (≤4 per call, looping in groups per the same convention as Step 2's question batch; options `Close` (default) / `Leave open`), naming the epic, its member count, and that every member reached a terminal (merged/verdict) state this run or a prior one. **The outcome this run is one of THREE, not two** (round-6 escalation HIGH finding — a failed write must not render identically to a decline): `closed`, `declined` (an explicit `Leave open`, or a genuinely unanswered call — per the kernel's merge-autonomy "timeout ≠ consent for a no-safe-default decision" rule, an unanswered call is never read as `Close`, so it collapses into this SAME `declined` outcome, indistinguishable from an explicit decline, both re-offered next run), or **`close-write-failed`** (the operator approved `Close` but the write itself broke). **On `Close`, the comment posts FIRST and is itself made idempotent** (round-7 escalation HIGH finding — a naive comment-then-write ordering re-posts "Closed by sweep" every time a prior write failed and the epic is re-offered): **probe for an already-posted closing comment before posting** — reuse the `comments` array item 2 above already read for `#E` (no extra call); if any existing comment's body starts with `Closed by sweep`, treat the comment as already posted and skip straight to the write below. **Otherwise, post it now** — `gh issue comment <E> -R "$repo" --body "Closed by sweep — all <N> member(s) drained via sweep. Run report: <this run's own Step-4 report, referenced by date/time>."`. **If that comment post itself fails,** warn-and-continue naming the epic, **skip the write this run** (the house comment-first convention — 2.6/4d-epic/triage-4.8 — never closes an epic unexplained), and record the outcome as `close-write-failed` so it is re-offered next run via the write-failed report row below. **Once the comment is confirmed posted (or found already present), attempt the write:** `if declare -F board_close_done >/dev/null 2>&1; then board_close_done "$BOARD" <E>; else gh issue close <E> -R "$repo"; fi` (the same `if`/`else` — never `&&`/`||` — fallback shape Step 3's spike-close arm uses, and for the identical reason: a transient `board_close_done` failure must warn-and-continue naming the epic, never silently fall through to a bare close that stripped neither the `fnd:status:*` label nor the `fnd:host/session:*` stamp). **If that write exits 0, the outcome is `closed`.** **If it exits non-zero,** warn-and-continue naming the epic (unchanged) AND record the outcome as `close-write-failed` — an infrastructure failure on an *approved* close, kept structurally distinct from `declined` so a recurring write breakage is never misattributed as the operator repeatedly declining. **The epic is simply RE-OFFERED next run** — no mechanism here distinguishes "retry the write" from "ask again" (the combinator has no previously-approved-close input), so a write-failed epic re-enters `offer-close` next run exactly like any other still-fully-drained epic; the write-failed report row below already tells the operator why they're being asked again. **On `Leave open`:** report only, no write, outcome `declined`.
   - **`left-open-unattended`** (fully drained, unattended) → leave `#E` open; never close it. **Probe before append, keyed on the epic number, across the pending-decisions surface's WHOLE history — not just this run.** Read the surface (`Pipeline/pending decisions.md` vs the legacy `Context/pipeline - pending decisions.md`, path-fallback + append-target-resolution rules, `claude/commands/check-in.md`) and skip the append if **any** existing entry — `open` or already disposed — already names epic `#E` for this decision (match on `epic #E` in the Decision line). "One entry per epic EVER, not per run" is exactly this match: a disposed entry from a prior run still suppresses a fresh append the next time the same epic is found fully drained again. If no match, append one `### open` entry via `mcp__obsidian-builtin__vault_append` — **Decision:** *epic #E's members all reached a terminal (merged/verdict) state as of this run*; **Default taken:** *leave the parent open; no board close write*; **Disposition:** *auto-taken (operator-absent); every member's terminal state retained as the operational record*; **Status:** *open*. **This is the seventh `ask-at-checkin` writer site** (registered in `claude/CLAUDE.md § Unattended pending-decisions surface` and `tidy.md` Step 3 § Pending decisions surface).
   - **`progress`** (partially drained) → report only (§ Step 4): closed/total member count, plus — for any still-open member that also appears in Step 1 items 4/5's blocked-frontier data this run — the blocker attribution for why it hasn't landed; a still-open member with no recorded blocker is named plainly as "not yet driven."
   - **`no-progress`** → omit from the report entirely; nothing changed for this epic this run.
5. **Tally as each epic is evaluated:** `epics_reviewed` += 1 per epic evaluated this step (every branch above, including `cannot-establish`); `epics_closed` += 1 only on outcome `closed` (an actual, successful `board_close_done` / `gh issue close` write); `epics_left_open` = `epics_reviewed − epics_closed` (every other branch AND outcome, including `declined` and `close-write-failed` — the tally is arithmetic-only and does not distinguish the two; that distinction is the Step 4 report's job alone, via the seventh row shape below).

### B. Emit the run telemetry record

`/sweep` has no plan-note footer, so without an explicit emit here a whole run — or a run that silently stopped emitting — produces **no** signal at all (the June silent-failure class: a never-written stream is indistinguishable from "nothing to do"). Once Step 3.5's assertion passes (every Phase-2 entry has a terminal disposition) and Subsection A above has produced its three epic counts (the zero-epic fast path's zeros count), append ONE command-run record from the checked-off Phase-2 checklist plus those three counts — this single call is the executable emit point, not a prose reminder, and its presence is mechanically enforced by `workflows/scripts/validate-command-run-emit.sh` (wired into `scripts/quality-gates.sh`), which fails CI if this invocation is removed: <!-- cite: SW.10 guard:workflows/scripts/validate-command-run-emit.sh -->

```bash
"$(git rev-parse --show-toplevel)/workflows/scripts/emit-command-run.sh" \
  --command sweep --board "$BOARD" --target "$BOARD" \
  --items-processed <Phase-2 checklist size> \
  --merged <count of "merged" terminal dispositions> \
  --resolved <count of "resolved (verdict)" terminal dispositions> \
  --parked <count of "parked" terminal dispositions> \
  --epics-reviewed <Subsection A's epics_reviewed> \
  --epics-closed <Subsection A's epics_closed> \
  --epics-left-open <Subsection A's epics_left_open>
```

**The three disposition counts MUST partition `--items-processed`,** exactly as before this step existed. Step 3.5 already asserts every Phase-2 entry reached exactly one of `merged` / `resolved (verdict)` / `parked`; this is that assertion carried into the record, and the emitter enforces it (`merged + resolved + parked == items_processed`, else a non-zero exit naming the arithmetic). Before temperloop#1084 there was no `--resolved` at all, so a spike closed on its verdict had to be folded into `--merged` or dropped — the latter is what happened, producing records like `{items_processed:30, merged:27, parked:1}` in which two items were simply unaccounted for. If this doc's terminal set ever gains a fourth disposition, add its field to the emitter in the same change: padding `--items-processed` to make the arithmetic close is exactly the silent under-report the check exists to prevent.

**The epic counts are a SEPARATE, independent partition — never folded into `--items-processed`.** An epic is never one of the Phase-2 pooled issues (it is the *parent* those issues belong to, reviewed only after all of them are already disposed), so `epics_reviewed`/`epics_closed`/`epics_left_open` never touch the items-side arithmetic above; the emitter enforces `epics_closed + epics_left_open == epics_reviewed` as its own check, independently, with its own non-zero exit and its own named arithmetic on a mismatch. **This rides the SAME single `emit-command-run.sh` call as Subsection B's existing invocation — never a second emit call.**

Resolve the script bare repo-relative (same convention as `workflows/scripts/build/build.config.sh` in Step 0.4) — if it is absent from a non-vendoring checkout, the `"$(git rev-parse --show-toplevel)/…"` path simply fails to execute; treat that as a no-op and continue (never let a missing/failing emit block or delay the report). The script stays `|| true`-safe for *infrastructure* failure: a write failure warns to stderr and exits 0. Exit 2 is the one loud case — either accounting mismatch above; recount and re-emit, but never let it block or delay the report.

## Step 4 — Report

End with a re-orientation block. **The report must enumerate a terminal disposition for every Phase-2 pooled issue** — no issue may appear without one of `merged`, `resolved (verdict)`, or `parked`. (This is automatically satisfied when Step 3.5 passes.) For sweeps larger than five singletons, list all issues in a table (issue# | title | disposition | detail) so the operator can scan the full set at a glance rather than inferring coverage from aggregates.

- **Fixed** — each issue → its merged PR#.
- **Resolved (verdict)** — each spike issue → closed-directly note.
- **Parked (open question)** — each issue → the question / reason it parked, and that it carries `needs-clarification` for the next run's Phase 1.
- **Parked (risk-gate)** — each issue held by the member-bearing-chunk regime-selection gate (Step 3) → the PR#, the reason line(s) gate.sh returned (or the synthesized ERROR/non-zero-exit/malformed-JSON line), and that it stays claimed In Progress with the PR open (unlike an open-question park, it does NOT return to `Ready`/Phase 1 automatically — resolution is a human merge by hand, or the operator explicitly moving it back to `Ready` to re-enter a future pool; there is no re-offer).
- **Parked (not driven — chunk invocation refused/unavailable)** — each issue whose chunk's build invocation was refused or unavailable (Step 3's refused-invocation disposition). Report these **separately from the open-question parks above**, since their cause is machinery, not ambiguity: they carry **no** `needs-clarification` label and re-enter the next run's pool directly. Repeat Step 0.7's remedy line here so the operator can fix the cause before re-running, and say plainly that these issues were **not attempted**, so the run's coverage is short by that count. They count under `parked` in Step 3.6's record.
- **Skipped (flagged, unanswered)** — issues left flagged in Phase 1 (deferred / operator-absent). These are NOT Phase-2 pool members (they were filtered out in Step 2) and thus not subject to the Step-3.5 assertion — but they must still appear in the report.
- **Skipped (funnel-escalated)** — Ready singletons carrying `funnel-escalated` dropped from the fix pool in Step 1 (a stuck 5c code item with an open/failed PR awaiting the operator's manual merge/close, #697). NOT Phase-2 members; report them so the operator sees they were surfaced, not silently swept.
- One line: open-question parks + skipped issues re-enter the next `sweep` run's Phase 1 automatically (the self-healing loop) — a risk-gate park does NOT (see above).
- **Admitted Operational epics (informed pool report, epic #1847).** When Step 1 item 6 admitted at least one epic this run, a distinct block naming each admitted epic (`#E <title>`) and, under it, **every one of its admitted members' issue-body acceptance text verbatim** — the same acceptance bullets Step 3's worker prompt was built from — so the operator reading the report sees the full named set of what was authorized to drive, not just an aggregate count (informed named-set consent). A run that admitted nothing omits this section entirely (no empty header).

**Residual blocking findings section (temperloop#1970).** A distinct block, rendered whenever any Phase-2 issue's `park()`-returned `review.residual_blocking` is non-empty — read straight off each chunk's `build-level.mjs` parked records, the same place this step's other per-issue detail comes from. One row per affected issue: `#N <title> → PR #<pr> — §3e round <round>/<max_rounds>, UNRESOLVED HIGH carried in the PR's ## Review notes`. State plainly, once, under the rows: **those `## Review notes` MUST be read before merging the PR** — the §3e convergence bound (Step 0.4's `reviewBlockingMaxRounds` hand-off) stopped the re-escalation loop, it did **not** resolve the finding, and the finding is carried verbatim, never suppressed. A run with no residual entries **omits the section entirely** (no empty header) — but never omits it when one is present: the affected issue's own disposition row above still reads `merged`/`parked` identically to a cleanly-reviewed one, so this block is the only place the unresolved HIGH is visible outside that one PR body.

**Degraded-routing rows (temperloop#2020).** The same block carries one row per issue whose `park()`-returned `review.routing_degraded` is present: `#N <title> → PR #<pr> — §3e reviewed on a PARTIAL roster (<the gap's own missing/mismatch figures>)`. That issue's `reviewer-routing.tsv` relay did not survive, so its **extension-axis and prose-`*.md` routes were never resolved** and whichever reviewer those rows would have named did not run; the table-independent routes (the mandatory command-doc rule, `review:`, `kind: architectural`) did run, so `ran` and `mandatory_ok` read clean for an issue whose `.sh`/`.mjs` diff went unreviewed. Same omit-when-empty, never-omit-when-present rule as the rows above, and for the same reason.

**Epic-closing gate section (Step 3.6A, epic #1847).** A distinct block, present whenever `epics_reviewed > 0` this run (omit entirely on the zero-epic fast path — no empty header). One row per reviewed epic, `#E <title> → <verdict-line>`:

- **Closed** — `#E → closed (N/N members drained)`, the closing comment's own pointer back to this run's report.
- **Offered, declined** — `#E → offer declined this run; N/N members drained, will be re-offered next run`. Covers both an explicit `Leave open` answer and a genuinely unanswered call (per the kernel's timeout-≠-consent rule, the two are indistinguishable here) — **never** a `close-write-failed` outcome, which gets its own row below.
- **Close approved but write failed** — `#E → close approved but write failed this run (<one-line error>); will be re-offered next run`. The `close-write-failed` outcome (round-6 escalation HIGH finding): the operator approved `Close`, only the comment post or the `board_close_done`/`gh issue close` write itself broke — kept distinct from "Offered, declined" so a recurring write breakage is never misattributed as the operator repeatedly declining. Tallied under `epics_left_open` exactly like a decline, but never rendered as one.
- **Left open (unattended, fully drained)** — `#E → fully drained (N/N); left open — pending-decision entry <recorded | already on file>`.
- **Keep-open** — `#E → keep-open (ask <assignee/last-toucher>); M/N members drained`.
- **Progress** — `#E → M/N members drained; still open: <#issue (blocker attribution) | not yet driven>, …`.
- **Cannot establish** — `#E → drain state unknown this run (<which read failed>); re-checked next run`.

One closing line: `epics_reviewed=<N>, epics_closed=<N>, epics_left_open=<N>` — the same tally riding this run's `emit-command-run.sh` record (§ Step 3.6B), so the human line and the machine record never disagree.

**Blocked-frontier section (temperloop#1835).** A distinct block, always present when Step 1 items 4–5 deferred anything this run (omit the section entirely on a run with nothing blocked — no empty header). Two subsections:

- **Blocked on an open dependency** — one row per item Step 1 item 4 deferred: `#N <title> → blocked by #B1[, #B2, …]`. A read-failure deferral (Step 1 item 4's call-failure handling — the `board_blocked_by_open` call itself errored, no blocker numbers were ever read) renders instead as `#N <title> → blockers unknown (read failed this run — re-checked next run)`, and is excluded from the multi-run-stall comparison below (which matches on exact blocker-set strings; a read failure never produces one). Any other row whose issue already carries an earlier-dated `Blocked by sweep (blocked_by):` marker comment (Step 1 item 4's durable trail) is annotated **`(multi-run stall since <date>)`** — it was already blocked as of a prior run, not first parked here.
- **Blocked_by cycle detected** — one entry per cycle the Step-1 item-5 pool walk surfaced: the full member list in a `#A → #B → #C → #A`-style chain (or the walk's raw membership if the exact loop order isn't reconstructed), plus any items reported as transitively unresolvable behind it. State plainly: none of these items are driven while the cycle stands, and it will not self-resolve without a human clearing one of the edges.

These items are NOT Phase-2 pool members (dropped in Step 1, same as a funnel-escalated skip) and thus not subject to the Step-3.5 terminal-state assertion — but every one of them must appear here so the operator can see and act on the frontier rather than have it silently reproduce identical, unexplained defers run after run.

End with a compact **refs legend** (qualified issue/PR numbers → title) per the communication conventions.
