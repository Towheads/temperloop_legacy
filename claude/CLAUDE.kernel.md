# Global guidance

## Kernel vs overlay routing rule

This file (`claude/CLAUDE.kernel.md`) is the **shippable kernel contracts doc** — the
generic process rules a stranger's fresh install of the open-source kernel repo would
need. Its sibling `claude/CLAUDE.overlay.md` carries everything personal/org/machine-
specific (Travis's Obsidian vault, session-log hooks, personal decision-capture rules,
personal paths and boards). `workflows/scripts/install-claude-md.sh` composes both
(plus a rendered knowledge-store-routing section, and any `{{SETTING_NAME}}` placeholder
tokens this kernel doc's own prose contains — § Named-setting convention below)
into the single installed `~/.claude/CLAUDE.md`. (The foundation fleet wraps that
script as `make install-claude`; a standalone kernel checkout runs the script
directly — this repo's Makefile deliberately carries no `install-claude` target.)

Routing test for **where a new rule belongs**, applied when adding or editing a rule: <!-- cite: K.1 incident:F#1050 -->

- **The stranger test.** Would a stranger's install — someone who cloned only the
  kernel repo, with no org tied to this repo's history, no Obsidian vault, no personal board — need this
  rule for the kernel machinery (board adapter, build/sweep pipeline, install/doctor,
  branch/PR policy) to work correctly? If yes → **kernel repo**, and the change should
  land **upstream first** (never patch a vendored copy of the kernel in a downstream
  overlay repo silently — the kernel repo is the source of truth for kernel content,
  exactly as this repo already is for the board toolkit and build machinery synced into
  stageFind/ssmobile/subsetwiki).
- If the rule is personal, org-specific, or tied to one machine's paths/credentials →
  **overlay**.

Corollaries:

- **Kernel edits land upstream first.** A kernel-repo rule is never patched only in a
  downstream overlay checkout — that silently forks the contract and the next kernel
  sync clobbers or conflicts with it. Fix it in the kernel repo, then let it flow down.
- **Ambiguous foundation-domain captures default to kernel.** When a new rule is
  genuinely unclear which side it belongs on, but it concerns foundation's own pipeline
  machinery (board adapter, build/sweep, install/doctor, quality gates) rather than
  Travis's personal environment, route it to kernel — the cost of a kernel rule that
  turns out unused by a downstream adopter is low; the cost of an overlay rule that
  silently governs shared machinery is a hidden coupling the split is meant to remove.
- **Overlay may extend, never contradict.** The overlay file may add personal rules and <!-- cite: K.2 class:kernel-contract-fork -->
  elaborate on kernel rules with machine-specific detail, but it must never state
  something that conflicts with a kernel contract (e.g. a different branch/PR flow, a
  different required CI check name). A contradiction is a kernel-repo bug to fix
  upstream, not something to route around downstream.
  - **Carve-out: named message templates — most of them, not all.** The one
    deliberate exception is a **named template defined in
    `claude/message-schema.md`** (e.g. the PR-body skeleton, the parking note) —
    that file's own § Overlay override status declares **which** of its named
    templates are the sanctioned surface an overlay may redeclare by name.
    Read the exclusion, not only the exception: that file also names a
    **non-overridable set** (currently its § Decision presentation, whose
    five-part shape and plain-language rule *are* a challenge gate, so a
    redeclaration could hollow the gate out), and a template in that set stays
    fully governed by the "never contradict" default above. The exclusion is
    mechanically enforced rather than prose-enforced —
    `workflows/scripts/validate-template-refs.sh` fails an overlay that
    redeclares a listed name. So: this supersedes "never contradict" for the
    *sanctioned subset only*; it does not license an overlay to diverge from any
    other kernel contract (a different branch/PR flow, a different `checks`
    name, or a parsed/frozen surface per `claude/presentation-plane.md`
    remain non-overridable). The redeclaration mechanism itself (precedence,
    dangling-override detection, the non-overridable set) is specified by
    `message-schema.md`'s own `## Overrides` section — this carve-out only
    states which surface is sanctioned, not how the override resolves.

## Capture/Backstop pairing

When adding or modifying a real-time extraction rule (e.g. decision capture, config-drift detection, feedback memory, session optimization tracking), also add the corresponding backstop in `~/.claude/commands/tidy.md` Step 3 **in the same change** and register the pair in a registry table. There are two: `tidy.md`'s own top-of-file table is the **single source of truth for KERNEL pairs** (generic enough that a stranger's kernel-only checkout needs them backstopped too); a composed/overlay checkout additionally carries `claude/capture-backstop-registry.overlay.md`, the **overlay extension table**, for pairs whose capture half is a personal/vault-backed rule with no meaning in a standalone kernel checkout. Route a new pair by that test. The two halves of a pair (capture + backstop) are a single feature with two surfaces — never ship only one. `foundation/workflows/scripts/validate-capture-backstop.sh` parses the kernel table always, and unions in the overlay extension table when present, in CI (the `checks` gate) — it **fails the build if any pair, in either table, is half-present**, so a capture rule shipped without its backstop (or vice versa) is caught mechanically, not by review. See [[Patterns/Capture-Backstop pairing]] for rationale and edge cases. <!-- cite: K.3 guard:workflows/scripts/validate-capture-backstop.sh -->

## Mandatory-step birth rule

Declaring a pipeline step **mandatory** and shipping its **execution signal** are two halves of one change — never the first without the second. A step whose spec says it must run, with nothing observable proving it ever did, is undetectable except by archaeology: `/build` §3e's command-doc reviewer pass read "mandatory" for ~a month while the default path structurally could not spawn a reviewer at all, and the *installed* orchestrator once ran six days stale through a whole batch — both invisible until someone diffed two files by hand. An **execution signal** is one of four shapes, all checkable from a checkout: a **per-run tally** the executing code emits (`build-level.mjs`'s `review: { ran, skipped, mandatory_ok }`, surfaced in the Step 6 summary), a **static guard** in a `checks`-wired suite that goes red if the step's invocation is removed, a **runtime refusal** by the producing code, or a **coverage rollup** of the step's execution rate. Prose restating the declaration is never a signal. Enforcement is the § Capture/Backstop pairing shape, not a second one: the pair is registered in `workflows/scripts/config/mandatory-step-registry.tsv` and `workflows/scripts/validate-mandatory-step-signal.sh` fails the build on a half-present pair. Because a registry nobody remembers to edit is the same failure one level up, it also **discovers** mandatory declarations mechanically from `claude/commands/*.md` and fails any with no disposition — and its `pending` debt ledger is shrink-only, so a *new* declaration can never be parked instead of signalled. <!-- cite: K.52 guard:workflows/scripts/validate-mandatory-step-signal.sh -->

## Named-setting convention

A command spec (`claude/commands/*.md`) is AI-executed prose, not a program — a <!-- cite: K.4 incident:K#164 -->
tunable value (a poll cadence, a cap, a window) embedded directly in that prose
can only be changed by a model re-reading and re-editing the spec text itself.
The rule (D3, temperloop#164/#169/#183): **prose names a setting, never states
its value.** Two sites, two
render times, because a command spec executes at run time but a standing-rules
doc like this one never executes at all:

- **Command-spec settings (runtime).** A command spec's early "Step 0" sources a
  config script — the existing convention is `source
  workflows/scripts/build/build.config.sh` (bare repo-relative, matching the
  build-machinery scripts), which is the ONE place a batch-pipeline setting's default
  lives (see that file's own header). Every later prose reference in the spec
  then names the setting symbolically (`$SETTING_NAME`, or the belt-and-suspenders
  `${SETTING_NAME:-default}` form for a consuming repo that doesn't vendor the
  config file) instead of restating its value inline. `claude/commands/build.md`
  Step 0 item 6 is the worked example — it sources `build.config.sh` once,
  early, and every later setting reference in that spec (`BUILD_MERGE_GATE_WINDOW`,
  `BUILD_QUOTA_PAUSE_PCT`, etc.) is symbolic from that point on, never a bare
  literal. A new command spec with a tunable value follows the same shape:
  source the config file at Step 0, reference `$SETTING_NAME` everywhere after.
- **CLAUDE.md-resident settings (compose time).** A setting inside a standing rule in
  this file (e.g. the epic-decomposition sub-unit threshold below) has no Step 0 to source from — the doc is
  read passively, never executed — so it renders at **compose time** instead,
  through the same seam `install-claude-md.sh` already uses to render its
  "## Knowledge store routing" section (§ Kernel vs overlay routing rule
  above): the script resolves the value from `build.config.sh` and substitutes
  it into a `{{SETTING_NAME}}` placeholder token in the kernel doc's own text
  before writing the composed file. No new templating engine — one more
  config value resolved into the same render pass.

Both halves migrate the kernel's remaining prose-embedded tunables
incrementally (temperloop#183 establishes the two seams; a later item migrates
the rest of the fleet) — an un-migrated literal elsewhere in this repo's prose
is a known gap, not a contract violation of this rule.

## Trust confirmed state

Don't spend a round-trip re-checking state you've already confirmed: <!-- cite: K.6 keep:2026-07-25 -->
- No `git pull`/`git status` right after your *own* push or merge — the tree is current by construction.
- Trust a green `gh pr checks`/CI result (or a `--watch`/poll that already exited 0); only re-poll on a non-zero or `UNKNOWN`.
- A confirmed diagnosis explains its downstream symptoms — don't re-probe to "confirm" what you already established.
- Don't re-read a file you just wrote to "verify" it — the write tool already errored if it failed.
- Don't re-fetch a value you already hold through a heavier path — reading one board field with a fresh `gh issue`/`gh api` call after the adapter's resolve already cached it (`BOARD_ITEMS_JSON` carries it) bypasses the cache and spends a round-trip for nothing. Reaching for a heavier tool to read a single value you resolved earlier is the tell. <!-- cite: K.5 incident:F#53 -->

## Tool invocation discipline

The friction ledger's dominant recurring class is tool misuse that a ten-second read would have prevented. Three guards, promoted from repeated live evidence (K#422): <!-- cite: K.7 incident:K#422 -->

- **Load a deferred tool's schema before its first call.** A tool listed as deferred (`Monitor`, `TaskUpdate`, MCP tools named in a system reminder) fails `InputValidationError` when called cold — run `ToolSearch "select:<name>"` first. On an unattended run this class has stalled an entire pass (foundation#1201).
- **Read a script's usage header before invoking it with guessed flags or env vars.** A guessed flag (`capture.sh --title …` — the title is positional) costs a round-trip when it errors, and a guessed env override (`COMMAND_RUN_RAW_DIR` vs the real `CMD_RUN_RAW_DIR`) can silently succeed against the wrong target. Same rule for sourced libs: call only helpers the lib actually defines — read it, don't guess accessors.
- **Check the platform's dialect before leaning on a flag or regex feature.** macOS ships BSD tools: no GNU `timeout`, no `\?` in basic-regex `sed` (use `sed -E` / `gtimeout`). A silently no-op'd expression that happens to agree with your hypothesis is the expensive kind of wrong.

## Fetch ground truth before building

Probe current state before you mutate or build on it — stale assumptions cause the most expensive rework: <!-- cite: K.8 guard:claude/hooks/git-stale-branch-guard.sh -->
- Before branching or opening a PR: `git fetch` and check `git log origin/main..HEAD` for divergence, plus `gh pr list --head <branch>` for an existing PR — don't build on a stale checkout or re-create a PR that already exists.
- Before a file move/delete that a decision might govern, check the vault (or repo history) for why it's there.
- A board's auto-add (or any async automation) can lag — wait/poll before concluding it "didn't fire."
- A bad experience with one *instance* isn't evidence against another. Before vetoing an approach on the strength of a prior failure, measure the specific case in front of you — a different backend, host, or config can invert the result the prior was based on.

The branch half of this rule is now **mechanically backstopped**: the `git-stale-branch-guard.sh` PreToolUse hook (foundation #590, the hook #49 deferred) intercepts `git checkout -b` / `git switch -c` off a local default branch, fetches origin, and `ask`s — naming behind-by-N — when the local base is stale. It only fires on the genuinely-stale case (branching off `origin/<default>` or an up-to-date local base stays silent) and fails open, so it backs the habit without replacing it.

## Measure the delta, don't assume it

A change is not an improvement until the improvement is measured. Capture the load-bearing number *before* a change and again *after* it, and let the before/after delta — not the plausibility of the change — decide whether it stays, grows, or reverts. This is the companion to § Fetch ground truth above: ground-truth probes the state you're about to act on; this probes the state you *changed*. The failure it prevents is shipping something that felt better but moved nothing (or moved the wrong number) — never assume a change is good because it seems like it should be. <!-- cite: K.9 keep:2026-07-25 -->

## Fix the real problem, not the symptom

Reach for the root cause at the right altitude, not the quickest thing that makes the symptom go away: <!-- cite: K.10 class:masked-recurring-defect -->
- **Never dismiss a test failure as "flaky."** Treat every failure as real signal and investigate it — a retry that makes it pass is a workaround, not a fix (`[[Patterns/foundation - retries are a workaround not a root fix]]`).
- **A broken build machinery or dev environment gets fixed first**, before you hand-roll a one-off workaround around it — the workaround masks the breakage for the next person too.
- **A fix scoped to one instance is a smell.** When a fix targets a single board/backend/host/instance, ask whether the real fix is one layer up — hoist the mechanism rather than patch the instance, or you re-patch every sibling in turn.
- **Disconfirm a root-cause diagnosis before institutionalizing it.** A root cause is a *hypothesis* until a cheap check fails to falsify it — so before you **propagate** one (file an issue on it, bake a warning into a spec or worker prompts, fan a fix across sites), run the **cheapest direct disconfirming probe the diagnosis makes available**: grep the file the theory names, check the binary is installed, read the config the mechanism assumes. The more expensive the propagation (an issue others act on, a warning that reshapes many prompts), the more a seconds-long falsification is worth running *first*. The failure this prevents: a false root cause ("a SwiftLint autocorrect build phase rewrites files mid-build") was baked into an issue and ~15 worker prompts and stood ~9.5h until a one-line `pbxproj` grep — available at diagnosis time — disproved it (no such phase; swiftlint not even installed). Companion to § Fetch ground truth before building (which probes the state you're about to *act on*); this probes the *diagnosis* you're about to *propagate*. (`/tidy` § Un-disconfirmed diagnoses is the backstop.) <!-- cite: K.11 incident:F#1090 -->

## A change isn't complete until it's reflected everywhere

A change that lands in one place but leaves its implications un-propagated is half-done: <!-- cite: K.13 class:stale-premise-resurrection -->
- **A new tool, script, or command wires its own discoverability in the same change** — the docs, the index, the `--help`, the place someone would look to find it — never "add it now, make it findable later."
- **When you reverse or supersede a direction, purge the superseded premise from every live artifact** — the issue body, the plan note, the open PR — not just the Decisions note that records the reversal. A stale premise left standing in a live artifact is how a rejected direction quietly comes back.

## Branch & PR policy

The build repos (foundation, stageFind, ssmobile, subsetwiki) share one branch/PR flow; this is **canonical** and their project `CLAUDE.md` files defer here rather than restate it. (A boardless/personal repo with no protected `main` is the exception — push freely there.) The kernel repo (`temperloop` — see § Kernel vs overlay routing rule) follows this same flow: it is a build repo like the others, not a special case. <!-- cite: K.14 guard:.github/workflows/ci.yml -->

`main` is **protected** — never push to it directly. Instead:

1. Branch `<type>/<slug>` — type ∈ `feat|fix|chore|refactor|docs|test`; slug kebab-case, ≤40 chars, descriptive. From a `/build` plan note the slug equals the item's `slug:` field.
2. Commit, then `git push -u origin <branch>`.
3. `gh pr create` — the body carries the verification surface (§ PR verification surface) and any `Closes #N` (§ Issue linkage).
4. Wait for the required **`checks`** status to go green. `checks` is the *contract*: every build repo names its required `.github/workflows/ci.yml` job `checks`, so "protected + green" means the same thing everywhere — but **what** `checks` runs differs per repo (see each project `CLAUDE.md`).
5. `gh pr merge` — **bare, with no method flag** — enqueues the PR in the repo's **merge queue**. It merges after clearing a *second* `checks` run, **not** immediately. **The queue owns the merge strategy, so do not pass one:** on a queue-required `main`, `gh pr merge --merge` is *rejected* ("merge strategy for main is set by the merge queue") — a method flag applies only to a repo with **no** queue, where `--merge` is what preserves merge commits. Every build repo here is queue-required, so the bare form is the one to use. **Omit `--delete-branch`** too — the queue rejects it; head branches auto-delete via repo setting. Branch-cleanup mechanics — the `delete_branch_on_merge` remote auto-delete plus the local/remote prune — are owned by `scripts/prune-merged-branches.sh` (its own usage header) and the `deploy-mini.sh` session-start sweep; see `docs/features/branch-hygiene.md`. <!-- cite: K.16 guard:scripts/prune-merged-branches.sh -->

**One-shot idiom — `pr-enqueue` (preferred for steps 3+5).** Rather than run `gh pr create` then `gh pr merge` by hand — and rediscover the two recurring frictions each session — use the **`pr-enqueue`** helper (foundation #534): a single command, run from **any** repo checkout, that resolves the canonical `owner/repo` and sets the gh default, creates the PR, enqueues it into the merge queue, and **confirms the queued state** — exiting non-zero with a clear message on any failure. It is deployed per-repo exactly like the board scripts (in the foundation fleet, `make install-board` puts it on PATH and `make sync-*-board` vendors it into consuming repos; a standalone kernel checkout — which ships no `install-board`/`sync-*-board` target — invokes `workflows/scripts/board/pr-enqueue.sh` directly). It kills two footguns: **(a)** a mismatched-casing/host `origin` (e.g. an `origin` whose owner casing differs from the canonical `Owner/Repo`) that otherwise breaks `gh pr create` with "No commits between …" / "Head repository can't be blank" until a manual `gh repo set-default`; and **(b)** the enqueue-method ambiguity — `pr-enqueue` enqueues with a **bare `gh pr merge`** (the queue owns the strategy), never guessing a method flag, and confirms via the `autoMergeRequest.enabledAt`/`mergeQueueEntry` GraphQL fields — deliberately never `isInMergeQueue`, which some installed `gh` versions reject outright and which temperloop#357 removed for exactly that reason (if a stray `--merge` is ever passed by hand and rejected, recovery is the same: re-run a bare `gh pr merge` and read "already queued to merge" — step 5 above now specifies the bare form, so the manual path no longer instructs the rejected one). **Never hand-roll that confirm, and note specifically that these are `gh api graphql` fields, NOT `gh pr view --json` fields:** `gh pr view --json mergeQueueEntry` (and `isInMergeQueue`) fails `Unknown JSON field`, because `gh pr view --json` exposes its own fixed field list rather than the GraphQL schema. That single wrong-surface call is the most-repeated tool-misuse in the friction ledger — fourteen recorded instances between 2026-07-03 and 2026-09-13. `pr-enqueue` already performs the confirm, so reaching for it by hand is never necessary; if you genuinely need the queue state directly, the working call is `gh api graphql` with a `repository(...){pullRequest(...){mergeQueueEntry{state position}}}` query. Typical use after pushing your branch: `pr-enqueue --title "<t>" --body "<b>"` (or `pr-enqueue --fill`). <!-- cite: K.15 guard:workflows/scripts/board/pr-enqueue.sh -->

Branch-naming rationale: `[[Decisions/foundation - Branch naming convention]]`. Pre-convention branch names a repo grandfathers in are noted in that repo's own file.

## Merge autonomy & consent

Autonomous merge is **scoped and revocable**, and operator silence is never consent for a decision that has no safe default. Three standing rules — the pipeline's mechanics already implement all three (`claude/commands/build.md` Step 4's regime-selected merge gate; the `ask-now` / `ask-at-gate` / `ask-at-checkin` partition in `[[Context/foundation - AskUserQuestion severity taxonomy]]`), and these state the *principle* at the standing-rules altitude so it is discoverable, not only the machinery:

- **Timeout ≠ consent for a no-safe-default decision.** Only a decision that *carries* a safe default may auto-proceed when a timed window elapses (the walk-away case, where absence of objection = consent). An `ask-now` decision — a structurally-risky merge set, a design-fork, a claim conflict — has **no** default by construction, so a timed-out or absent operator is **not** approval: the item parks and reports, it never proceeds on silence. The general principle behind this: a question is a request for a *decision*, not a license to *act* — neither the question's existence nor its timeout authorizes proceeding, and that extends to any external-system write (posting, publishing, pushing), not merges alone. <!-- cite: K.18 class:unbounded-autonomous-writes -->
- **A grant is scoped to the run or epic that earned it.** An autonomy grant ("merge the rest of this level without asking", "no approvals for the remainder of this epic") extends only to the remaining gates of that *same run or named epic*, at its stated quality bar — it is **never carried into a future session** (a fresh session re-earns it, it does not inherit it) and is **overridden by any later explicit pause**.
- **Only a clean, disjoint set is timed; a risky set is always modal.** The risk-tiered partition's mechanics are owned by `claude/commands/build.md` Step 4's regime selection + `workflows/scripts/build/gate.sh`; whether the autonomous merge tier runs at all is the `PIPELINE_DRIVE_MERGE` setting in `workflows/scripts/build/build.config.sh`, named here and never valued (§ Named-setting convention). <!-- cite: K.17 guard:workflows/scripts/build/gate.sh -->

**Operational escape — a deadlocked `/goal` Stop hook.** The "overridden by any later explicit pause" clause above needs a *mechanic*. `/goal` is a Claude Code built-in that sets a session-level completion condition; the harness's session-scoped **Stop hook** then blocks the session from ending until that condition is met or cleared. The kernel cannot modify this built-in, and Claude Code composes Stop hooks **any-block-wins** — so an added kernel Stop hook that returns "allow" cannot cancel it. When an active `/goal` (an autonomous-merge / "don't prompt" condition) conflicts with a later explicit operator pause on the very action that would satisfy the goal, the condition can **never** become true: every turn-end the Stop hook re-evaluates, sees the goal unmet, and **nag-loops indefinitely**. The escape is to **run `/goal clear`** to release the hook — the pause stands, and the hook's repeated re-prompting is **never** authorization to override it or to take the paused action. Author an autonomous-merge goal defensively so this can't arise: phrase its condition with an explicit escape ("…unless the operator issues an explicit pause, in which case the goal is satisfied") so a later pause deterministically clears it. See `[[Mistakes/foundation - Stop-hook goal conditions cannot implement polling loops]]`.

The *specific* grants an operator issues — a particular epic's "stop asking me", a repo's dogfooding "always get explicit approval before building" — are personal and operator-scoped: they live in the overlay, not here. This section states only the generic scoping-and-consent discipline that governs them.

## Working-tree ownership

**A session mutates only the working tree it was launched in.** Multiple Claude sessions share one machine's filesystem, and a git working tree has exactly one `HEAD`. Under the operating invariant **one session per repo directory**, a repo's *canonical checkout* is where a peer session lives — so reaching out of your own launch dir to mutate another repo's canonical checkout in place (a `git checkout -b`, a commit, a merge, the foundation fleet's `make install` — this kernel repo's own Makefile ships no `install` target) moves that peer's `HEAD`/branch pointer underneath it and leaves its on-disk state inconsistent with what it thinks it has. Branch-per-issue (§ Branch & PR policy) protects `main`; it does **not** address this — two sessions sharing one tree still contend for the single `HEAD`. <!-- cite: K.19 guard:claude/hooks/write-lane-guard.sh -->

Your **lane** is your launch dir (`$CLAUDE_PROJECT_DIR`) **plus any linked git worktree** (a linked worktree is ephemeral task scratch with its own `HEAD` — never a session's launch dir, so writing one steps on nobody). Cross-repo work is therefore done in an **isolated worktree off the foreign repo** — `git -C <foreign-repo> worktree add <path> -b <branch>`, worked under `<path>` — never that repo's canonical checkout directly. The vault, `/tmp`, and scratchpads are not git repos and are always in-lane. Note also that the foundation fleet's `make install` (above — no such target in a kernel checkout, which installs via `workflows/scripts/install-claude-md.sh` / `install-settings.sh`) writes global `~/.claude`, a shared side effect regardless of worktree — run it deliberately (operator-run or serialized), not mid-task from an arbitrary session.

This is mechanically backstopped by the **`write-lane-guard.sh`** PreToolUse hook (kernel `claude/hooks/`): a state-mutating tool call (Write/Edit/…; Bash `git commit|checkout|switch|merge|reset|push|…` or `make install`) whose target resolves to the main working tree of a repo other than home returns an `ask`, naming home vs. the foreign checkout and pointing at the worktree escape hatch. Home, any linked worktree, non-repo paths, `git worktree add`, and all read-only ops stay silent; the hook fails open. Same guard family as `git-stale-branch-guard.sh` / `subtree-edit-guard.sh`. Rationale: `[[Decisions/temperloop - Session write-lane guard]]`.

**Read-side companion — never revert a co-tenant's uncommitted work.** When a shared checkout has uncommitted changes **you didn't make** — a dirty tree that blocks your own `git pull --ff-only` or rebase — treat them as another session's live work: **surface them, don't revert them.** A blocked pull is a signal to identify ownership (`git status`; if the dirty files aren't yours, name them and their likely owner, then work in an isolated worktree or hand the checkout back), never a license to `git checkout -- .` / `git stash` your way past it — that destroys a peer's uncommitted state with no recovery. The write-lane guard above covers *your writes reaching a foreign tree*; this covers *your reverts erasing a co-tenant's uncommitted work in a shared tree*. Rationale: `[[Patterns/foundation - leave a co-tenant's dirty files untouched in a shared checkout]]`. <!-- cite: K.20 class:co-tenant-work-destruction -->

## Environment hygiene

Every local checkout, worktree, and launchd agent has a **role**, and each role owns its own definition of "clean." Drift accumulates silently otherwise — `build`'s own Step 0.5 recovers only the current run's stranded claims, and a leaked worktree or a cron checkout that quietly fell behind `main` otherwise goes unseen until someone trips over it. The clean-baseline-per-role contract: <!-- cite: K.21 guard:workflows/scripts/build/env-reconcile.sh -->

- **cron/kernel checkout** — must be **clean-on-main**: no uncommitted changes, `HEAD` on the default branch, not behind the last-fetched `origin/<default>`. Default checkouts: `foundation.cron`, the kernel checkout (`temperloop`), `foundation-kernel` (a pre-rename kernel-checkout name some hosts still carry).
- **operator/consumer checkout** — may **legitimately sit on a feature branch**; this is normal, in-progress human/session work, not drift. Its drift classes are narrower: a branch whose PR already merged (parked-on-merged), or stale untracked files. Default checkouts: `foundation`, `stageFind`, `ssmobile`, `subsetwiki`.
- **worktree** (`<repo>.wt/<slug>`) — **disposable** by definition (§ Working-tree ownership: a linked worktree is ephemeral task scratch, never a session's launch dir). A worktree whose PR has merged or closed, or that isn't a worktree its parent repo actually has registered, is leaked and safe to remove — removing it can never step on a peer session's `HEAD`. **Disposable is not unconditional, though: a worktree is removable only once its tree is *confirmed clean*.** Uncommitted work in a worktree is as unrecoverable as uncommitted work anywhere else, so a leak verdict over a dirty tree — or any verdict the classifier could not *establish* — is reported, never auto-removed, and the removal itself runs without `--force` so git's own refusal is the last belt (temperloop#658: a `fix/` worktree misread as leaked was force-removed and its uncommitted work destroyed). <!-- cite: K.51 incident:K#658 -->
- **launchd agent** — must be **loaded and fresh**: declared in `infra/launchd/*.plist` beside a checkout above, present in `launchctl list`, and showing evidence of a run within its own declared cadence.

**Policy: aggressive in-lane, report cross-lane.** Auto-fix is permitted only in checkouts that are structurally nobody's interactive home — a disposable worktree, or a cron/kernel checkout (role-defined as always clean-on-main, so drift there is safe to correct mechanically: a `git pull --ff-only`, a merged-branch prune). Drift in an **operator/consumer checkout** is never auto-corrected — per § Working-tree ownership, only the session that owns a checkout may move its `HEAD`, and an operator checkout may legitimately be another session's active lane. That drift is *reported*, never silently fixed by switching or resetting a foreign `HEAD`. The same reasoning holds for a launchd agent: never `launchctl load`/`unload` mechanically, since reloading an agent out from under a possibly-still-running process is exactly the foreign-mutation risk this policy avoids.

**The detection substrate.** `workflows/scripts/build/env-reconcile.sh` — read-only, fail-open — is the shared drift reconciler; its roles and its two probe formats (`--format report` / `--format entry`) are owned by its own usage header (`workflows/scripts/env-hygiene-report.sh` is its thin `--format entry` wrapper). <!-- cite: K.22 guard:workflows/scripts/build/env-reconcile.sh -->

**The `/tidy` audit surface.** `/tidy` runs a periodic, drain-internal **detect-and-propose** § Environment hygiene step (`claude/commands/tidy.md`) — a probe, not a capture/backstop pair, since environment drift is accumulated host *state* rather than an author action a capture rule captures. It runs both probe formats, then disposes each drift class per the aggressive-in-lane/report-cross-lane split above: a leaked worktree or a confirmed-clean cron checkout's `BEHIND_MAIN`/merged-local-branches get auto-healed on the spot; a foreign operator checkout's drift, or an unloaded/stale launchd agent, is appended verbatim to `Context/pipeline - environment hygiene report.md` (a knowledge-store pipeline surface, parallel to the pending-decisions and sensitivity-flags surfaces) for `/check-in` to review and dispose — `/tidy` never mutates a foreign checkout's `HEAD`. A drift class with no safe auto-heal that keeps recurring, or an auto-heal that itself fails, is filed as a board defect rather than left to re-surface silently every run.

This kernel section covers the detection + report/auto-heal contract only. The launchd **overlay** tail — `install-launchd-all` and `install-tidy-nightly.sh` defaulting agents to `foundation.cron` — is deliberately **out of scope here**; see `foundation#1089`.

## Issue linkage

Applies to **PR/issue workflows**: any time a PR resolves a GitHub issue. When it does, the PR body MUST carry a `Closes #N` (or `Fixes #N`) line so GitHub auto-links the PR and auto-closes the issue on merge. Omit it entirely for refactors, chores, or features with no pre-existing tracker — don't invent issue references.

Emit the keyword as **bare text on its own line** — `Closes #N`, never wrapped in backticks or a code span. GitHub silently ignores closing keywords inside inline code, so a backticked `` `Closes #N` `` merges the PR without closing the issue (the failure `/build` 3f guards against). The same prohibition covers commit messages merged to the default branch: a stray closing keyword in a *commit* auto-closes on merge too, so keep linkage out of commit messages and in the PR body alone (see `claude/commands/build.md` 3c/3f). <!-- cite: K.23 incident:F#265 -->

One PR can close **several** issues — but only when **each** carries its own bare keyword on its own line (`Closes #1` then `Closes #2`, never `Closes #1 and #2`, which closes only #1). This is useful for an **opportunistic same-PR fix** (a defect fixed alongside the planned work in the same PR) and a **root-cause-collapse atomic close** (a survivor's fix PR closing the survivor plus its absorbed symptoms together, so the cluster closes on one merge). In the plan pipeline this is the `also_closes:` field (`claude/plan-schema.md`): the primary issue rides `gh_issue:`, each additional one rides `also_closes:`, and `/build` (3f) emits one bare `Closes #M` line per entry.

This stays consistent with the rest of the pipeline. The plan-schema's optional `gh_issue:` field (`claude/plan-schema.md`) carries the issue number into a plan item; `/build` consumes it to inject exactly one bare `Closes #<gh_issue>` line into the PR body (3f), and items without `gh_issue:` emit no `Closes` section. Hand-authored PR bodies follow the same shape.

Bidirectional post-merge check: confirm the issue actually closed. Before merge, the PR body should show "Successfully merging this pull request may close these issues"; after merge, the issue's "Development" sidebar should show the PR and the issue should be **closed**. If an issue that should have closed is still open, the linkage was missed (usually a backticked or absent `Closes`) — fix the PR body or close the issue by hand, and treat it as a signal to check the generated-body path.

**Cross-repo closes.** A PR can auto-close an issue in **another** repo only via the explicit `owner/repo#N` form — e.g. `Closes <org>/stageFind#N` — emitted bare on its own line, never backticked, exactly like a same-repo `Closes`. A bare `Closes #N` is **same-repo only**: it never reaches across repos, so an issue tracked on the other board stays open if you use it. This is the caveat to state explicitly — a cross-repo close *requires* the fully-qualified `owner/repo#N` reference. <!-- cite: K.24 class:cross-board-issue-left-open -->

The motivating case is the foundation↔stageFind shared board tooling. The board scripts (`board.sh`, `claim`/`worklist`/`capture`/`reconcile`, etc.) are generated in **foundation** and deployed/synced into **stageFind**; when a foundation PR fixes shared tooling that is tracked by an issue on the *other* board, a `Closes <org>/stageFind#N` (or `Closes <org>/foundation#N`) line in that PR body auto-closes the cross-board issue on merge — removing a manual cross-board reconcile step that would otherwise be needed to mark the other board's item Done.

## Communication conventions

Guardrails so the operator never has to leave the conversation (or scroll far back) to understand what's being referred to. Born from a real board-numbering confusion (foundation#362).

- **Repo-qualify issue refs, with a first-mention title hook.** Whenever more than one repo is in play, write `stageFind#658` / `foundation#362` / `ssmobile#4` — never bare `#N`. Shorthand accepted in either direction: `S<N>` = stageFind#N, `F<N>` = foundation#N, `M<N>` = ssmobile#N, `W<N>` = subsetwiki#N, `K<N>` = temperloop#N. Per `claude/message-schema.md` § The reference-token rule, the *first* mention of any such ref in a response carries a short title hook drawn from its own title (≤6 words) — `stageFind#658 (board-numbering confusion)` — bare refs are fine for re-mentions after that. <!-- cite: K.26 incident:F#362 -->
- **Board identity is named, not numbered, in prose.** Boards are referenced by **name** in prose — "the stageFind board" — never by a bare board id a reader must resolve from memory; a raw number (`--board 3`) appears only inside a literal, copy-pasteable command line.
- **Refs legend — superseded.** The former rule ("any response that references issue/PR/epic numbers ends with a compact legend") is **superseded** by `claude/message-schema.md` § The reference-token rule: a trailing reference legend is reserved for long, non-linearly-read **mode-6 durable artifacts** (PR bodies, plan notes, decision notes) — ordinary responses use the first-mention hook above instead, never a legend.
- **Completion summary.** On completing a work item (fix merged, issue closed, batch level cleared), front-load the outcome — BLUF, `claude/message-schema.md` Tier-1 finding 1 — then give the reader the Endsley perception→comprehension→projection shape for a cold return: what changed, what it means for the item as a whole, what's next. <!-- cite: K.28 incident:K#94 -->
- **Resume recap.** The first response after a session resume or a long gap opens with one line on the active item and where it stands (the same Endsley shape, compressed to one line), before answering the new message.
- **Capture terminology at source.** When a taxonomy/terminology confusion surfaces mid-session, fix the canonical glossary (this file, or the project `CLAUDE.md`) in that same session — a verbal clarification alone is how the same confusion recurs. <!-- cite: K.30 keep:2026-07-25 -->
- **Print handoff URLs in full.** An artifact, report, or dashboard URL handed to the operator is printed in full at least once — never only a truncated or shortened form they can't click or copy.
- **Human-facing dates/times render in `{{DISPLAY_TZ}}`, never UTC.** Every date or time shown to the operator — a completion summary's timestamp, a by-day breakdown, a "last run" age — renders in the configured display timezone (`{{DISPLAY_TZ}}`, an IANA name so DST is automatic), not UTC. This matters most when **bucketing UTC-sourced data by day**: GitHub API and telemetry-lake timestamps are UTC, and grouping them on their raw UTC date splits the operator's evening across two calendar days (the confusion this rule prevents). **Convert to `{{DISPLAY_TZ}}` before you group or label by day.** Watch the specific footgun that jq's `strftime` **ignores `TZ` and always emits UTC** — use `strflocaltime` (with `TZ` set) for local bucketing; the same trap exists wherever a formatter silently defaults to UTC. **Carve-out — stored/parsed records stay UTC.** Machine-stored or machine-parsed timestamps are the deliberate exception and remain ISO-8601 UTC: the telemetry data lake, board claim/capture timestamps, and the plan-schema consent timestamp (a frozen surface — `claude/presentation-plane.md`). Localizing those would corrupt parseable records and break DST-free interval math. The rule is *display in local, store in UTC* — never the reverse. <!-- cite: K.27 class:corrupted-stored-timestamps -->
- **Plain terms before shorthand.** Give plain context before falling back on issue/board shorthand or internal jargon, and decide low-stakes bookkeeping yourself rather than surfacing it as a question. The shorthand is a re-mention convenience (the first-mention hook above), not the first thing a reader should have to decode.
- **Load-bearing context goes inside the question or final message.** Mid-turn narration is not reliably surfaced to the operator, so any context a decision depends on belongs in the `AskUserQuestion` block itself (or the final message) — not in prose emitted earlier in the same turn. <!-- cite: K.29 class:unsurfaced-decision-context -->
- **A denied action reports EVERY unblock path, and leads with the grant.** When a permission control refuses an action — the auto-mode safety classifier, a PreToolUse hook, a missing scope — the operator-facing message names all three paths, ordered so the one that restores autonomous progress comes first: **(1) grant the capability** (the specific permission and how to give it — a Bash permission rule, an interactive approval — scoped as narrowly as the action needs), **(2) run it yourself** (the exact copy-pasteable command(s)), **(3) drop or reroute it** (what is lost by skipping). Offering only path 2 silently picks the slowest option, reads as terminal when one word from the operator would resume autonomous progress, and converts a reversible policy choice that is theirs to make into a workload transfer; naming all three in an issue comment they never read does not count (see the bullet above). This is honest *reporting* of a denial, never license to retry it in a different shape — bypassing the denial's intent stays prohibited. Message shape, and the recorded no-backstop call: `claude/message-schema.md` § Degradation notice (denied-capability variant). <!-- cite: K.54 incident:K#1478 -->

## Response-level grounding citations

When knowledge-store content materially informed an answer, the response says so **in that same response** — `[source: <note path>]` naming what it drew on; and when a store query behind a context-dependent claim came back empty, it says *that* explicitly ("no relevant knowledge-store content found") rather than answering on from general knowledge as though grounded. Scope is the store seam alone (`workflows/scripts/lib/knowledge_store.contract.md`) — code the session read in front of it, and general knowledge, owe nothing; a citation is owed by an assertion's **provenance**, never by its topic. Why per-response rather than per-session: without it **memory bypass is undetectable at the only granularity that matters** — a grounded answer and one that merely *sounds* informed are indistinguishable to the reader, so retrieval can silently stop contributing while every answer still reads exactly the same (the placebo trap), and no instrumentation upstream of the answer closes that gap because the bypass happens downstream of it. `claude/commands/tidy.md` § Missing grounding citations is the paired backstop. <!-- cite: K.53 class:undetectable-memory-bypass -->

## Board reads and writes — always via the board.sh adapter

For ANY board read or write, **reach for the adapter first** — never a hand-rolled `gh issue` / `gh api` call against the tracker's own state. Two reasons. **Encoding:** the adapter is the single place that knows how item state is *represented* — Status, claim stamps, and work class ride `fnd:`-namespaced repo labels, with native milestones, sub-issues and issue-dependency edges alongside (`workflows/scripts/board/ISSUES-ONLY-BACKEND.md` is the vocabulary). A hand-rolled call re-derives that vocabulary by eye and gets it subtly wrong — the recurring shape is a bare `gh issue close` that closes the item but leaves its `fnd:status:*` label and `fnd:host/session:*` claim stamp behind. Be precise about what that costs, because the *Status* read is not the casualty: on the issues-only backend the reshape checks state **before** any label, so a closed issue reports Done no matter what labels survive (`workflows/scripts/board/ISSUES-ONLY-BACKEND.md` § Close→Done cascade). The residue is real drift all the same — it corrupts label-based queries, strands orphaned repo-level label objects, adds `reconcile.sh` sweep load, and leaves the item short of the definition of Done that § Board hygiene below gives it. **Cost:** the adapter caches a resolved board across processes and keeps single-item ops off the whole-board scan; a raw query bypasses that cache and re-pays for state already in hand. <!-- cite: K.31 incident:F#53 -->

Source it — `workflows/scripts/board/lib/board.sh` in foundation, `scripts/lib/board.sh` in stageFind — then use:
- **one issue** (its item id / status / fields) → `board_resolve_item <board> <issue#>` — cheap, no whole-board scan; the default for touching a single issue.
- **whole board** → `board_resolve <board>` once, then reuse the resolved state for many items (don't re-resolve per item).
- **just the items** → `board_item_list <board>`.
- **writes** → `board_set_status` / `board_set_milestone` / `board_set_component` / `board_set_number` (resolve-by-name; they bust the cache).
- or a **board command**: `worklist` / `claim` / `release` / `reconcile` / `capture` / `milestone`.

**Headless-run contract — source once per call, real helpers only, resolve before you set.** Shell state does not persist between separate Bash tool calls, so **every** Bash call that touches the board must `source` the lib *itself* — invoking `board_resolve_item` / `board_item_id` / `board_set_status` in a fresh call that didn't source `board.sh` fails `command not found`, the single most-repeated headless-session board misuse. Two more from the same cluster: (a) **use only helpers that exist in the lib** — read it, never *guess* an accessor (`board_item_status`, `board_get_field`, `board_opt_by_name`, `board_opt_value` do **not** exist); and (b) **`board_set_status` takes an `ISSUE_*` item-id, not a board number or an issue number** — resolve `board_resolve_item <board> <n>` → `board_item_id <n>` first (its arg guard rejects the wrong type, but the round-trip still wastes a turn). This rule is the companion to the adapter-first rule above: that one keeps you *on* the adapter, this one keeps the *adapter's own* invocation correct. See [[Mistakes/foundation - board.sh helper misuse in headless runs]]. <!-- cite: K.32 incident:F#1084 -->

**The board glossary** — two number spaces collide here; this table is canonical: <!-- cite: K.33 incident:F#362 -->

| Board id (`--board N`, the only number spoken in prose) | Name | Repo |
|---|---|---|
| **3** | stageFind build | `<org>/stageFind` |
| **4** | foundation build | `<org>/foundation` |
| **5** | ssmobile | `<org>/ssmobile` |
| **6** | subsetwiki | `<org>/subsetwiki` |
| **7** | temperloop | `<org>/temperloop` |

A board id is an internal key with no meaning outside the adapter — it needs only the `repo` axis wired up, in the built-in case map or a `boards.conf` line. Per-repo *issue* numbers are a second, unrelated space — qualify them per § Communication conventions. In prose about *issues*, use the `K<N>`/`F<N>` shorthand (§ Communication conventions); `--board 7` is the adapter handle, used by scripts (e.g. `capture.sh --repo kernel`). Every registered board also accepts its **name** in place of its id (`--board temperloop`), so a human never has to touch the number space at all.

## Task workflow (board-enabled projects)

This section governs **board-enabled projects** — those registered in the board adapter's registry (§ The board glossary above). In a project with no board (personal/boardless work), none of it applies; skip it. Where these rules name a *script*, run it through the board adapter per the board.sh-adapter rule above — never a hand-rolled tracker call. The board itself is read/written only via that adapter; this section is about *when and why* you touch it, not *how*.

**The In-Progress gate.** On a board-enabled project, no substantive work happens in a session except under an item in **In Progress** — and "substantive" includes investigation and planning, not just code. About to do real work with no In-Progress item covering it? Stop and create or move one first. Everything that happens is tracked; nothing gets silently abandoned. (For *non-trivial* work this composes with the plan-first habit — but the gate applies to any substantive work, trivial or not, on a board-enabled project.) <!-- cite: K.35 class:silently-abandoned-work -->

**Claim first — before you investigate.** The board is a cross-session lock, so the claim is the *first* action when an item enters In Progress — the user names an item, or you pull a Ready one. Claim **before** reading the issue in depth, exploring code, or reading vault notes: investigation and planning are themselves the duplicate-able work the lock protects, so claiming after them reopens the race a second session can double-pull through. A wrongful claim is cheap to undo (park it back to Ready per "Park, don't abandon"); claim-then-verify beats verify-then-claim. <!-- cite: K.36 class:cross-session-double-pull -->

**Session-start routine.** On a board-enabled project, before any work, list the In-Progress set (via the adapter's `worklist`) and ask which to resume — don't pick for the user, and don't start new work until they answer. <!-- cite: K.37 keep:2026-07-25 -->

**Park, don't abandon.** To set work aside, MOVE the item out of In Progress (to Ready or Backlog) and add a one-line parking note: where it stands + the next concrete step. A tracked status change, never a silent drop. (There is no `Blocked` Status bucket — it was retired in #435; a genuine dependency block is a native `blocked_by` edge, and an open *question* is the `needs-clarification` label, not a status.) <!-- cite: K.38 incident:F#435 -->

**Claim held until Done.** Distinct from parking-to-Ready above: an item that is *still being driven to completion* — most concretely a `/build` item parked `[m]` awaiting the batch merge gate — legitimately **stays In Progress with its claim HELD until it reaches Done**. This is the sanctioned flow, not drift. The board claim is a cross-session lock, and the work isn't finished until merge, so the claim's job isn't over at park; the board half leaves In Progress only via the close→Done cascade on merge or a deliberate skip (never a manual mid-flight release). Consequently, **releasing the local terminal claim marker at park is optional and best-effort, never a required step** — and it deliberately isn't relied on: `release.sh` is one-marker-per-window, so in a **multi-claim window** (the documented within-level parallelism, where one session claims several items at once) the marker holds only the *latest* claim and correctly **refuses** to clear a *non-latest* one. That refusal is expected and harmless under claim-until-Done — the earlier claim stays held and `reconcile.sh` / the cascade clear the board half on merge. The normal flow therefore never *requires* releasing a non-latest claim at park; a persistently-stranded In-Progress claim whose work is genuinely abandoned is disposed by "Park, don't abandon" above (move it back to Ready), not by forcing a per-window marker that points elsewhere. (Rationale: K#275 — stop requiring a release-at-park of a non-latest claim.) <!-- cite: K.39 incident:K#275 -->

**Capture at source + defect-vs-enhancement routing.** A thread that opens mid-work is never a bare aside. Part of the active item → add a checkbox to it. Separate → file it, then continue. Route by kind: a **defect** (something broken, a gap, a regression, untracked work that *should already exist*) → GitHub issue + board item (via the adapter's `capture`); an **enhancement or deferred design seam** (a future capability, a "consider later", a decided-but-unbuilt direction) → a vault `Decisions/` or `Context/` note (this is the live counterpart to the **Decision capture** rule above). When genuinely ambiguous, prefer the board — a Backlog item is cheap to close, a dropped defect is expensive to lose. **"Captured in a vault note" satisfies *rationale*, not *tracking*** — if the note names actionable work, it also needs a worklist item. <!-- cite: K.40 class:silently-dropped-defects -->

**Capture, don't ask.** When you notice a defect mid-work you are *not* fixing now, do **not** end the turn with "want me to file this?" and wait — that offer dies when the session ends, which is how bugs get dropped. File it immediately (adapter `capture`, with `--board 3|4` as appropriate) and mention you did. Filing is reversible; a silently dropped bug is not. Two sharpenings: **(a)** this is **defects only** — a *defect* (something broken, a gap, untracked work that should already exist) gets filed; a speculative *enhancement* does not become a Backlog item just to look tracked (route it per the defect-vs-enhancement split above). **(b)** The sharpest trigger is **working around** a defect: the moment you reach for a retry, a shim, or a manual step to route past something broken, file it in that same action — that is exactly when it is easiest to promise yourself you'll remember, and exactly when you won't. (`/tidy` § Unfiled defects is the backstop.)

**Board hygiene is part of the gate — and the Done write is yours to make.** The board is only a trustworthy parallelism substrate if it reflects reality, and **nothing moves an item to Done on its own**. Closing the issue makes the item *read* closed, but Done is defined as closed **with no** `fnd:status:*` label, and only the adapter's Done write strips that label (and the `fnd:host/session:*` claim stamp). So **`board_set_status … Done` is the PRIMARY mechanism, not a backstop** — owed by whoever closes the item, including after a merge's own `Closes #N` — and `reconcile.sh --status` / `--labels --apply` is the sweep for closes that bypassed the adapter (K#902: 9 of 9 closures needed the explicit move). Do not wait for an automation to do this; there is none, and nowhere to hook one. When you create an epic's sub-issues, add them to the board. The drift this prevents is a **disagreement**: an item reporting Done while still wearing its `fnd:status:*` label and a live `fnd:host/session:*` claim stamp, so label-based queries and the claim lock contradict the Status read — and because that claim stamp is the cross-session lock, a stranded one leaves finished work looking owned by a session that is gone. (The Status read itself never gets stuck at Ready/In-Progress: per § Board reads and writes above, the reshape checks state before any label, so a closed issue always reports Done.) If you find drift, fix it before pulling new work. (This composes with **Fetch ground truth before building** — probe the board's real state before relying on it.) <!-- cite: K.41 incident:F#130 -->

**Decompose epic-sized work up front.** For work that is epic-sized — **`{{EPIC_MIN_SUBUNITS}}`+ parallelizable sub-units, OR more than one dependency level** — do a design-decomposition pass *before* building: an epic (GitHub issue + board item) plus contract-scoped sub-issues grouped into dependency levels, captured as a `Plans/` note via `/assess`. Below that threshold, a single board item is right — don't manufacture an epic for one change. The decomposition is what unlocks parallel, batch-resolvable work (`/build` runs a whole level at once). (`{{EPIC_MIN_SUBUNITS}}` is rendered at compose time from `EPIC_MIN_SUBUNITS` in `workflows/scripts/build/build.config.sh` by `workflows/scripts/install-claude-md.sh`; see § Named-setting convention above. Edit the config, never this literal. The dependency-level half of the threshold stays a structural fact, not a separate setting — "more than one level" is definitional to when decomposition unlocks parallelism, not a tunable spectrum.) <!-- cite: K.42 guard:workflows/scripts/build/build.config.sh -->

**Decompose to the seam, not the implementation.** A sub-issue fixes its *contract* — what it **produces** (an interface, artifact, schema, or verdict), what it **consumes** (its deps), and its **acceptance check** — and says nothing about *how*. Contracts are what make issues both parallelizable (no coordination once the seam is fixed) and stale-resistant (an implementation learning changes the *how*, not the contract). A sub-issue body that starts prescribing implementation is the staleness smell — pull back to the seam. <!-- cite: K.43 class:mid-build-replan-churn -->

Rationale: `[[Decisions/stageFind - Task workflow (board + WIP-3 gate)]]`, `[[Decisions/stageFind - Contract-based epic decomposition]]`, `[[Decisions/stageFind - Dropped-bug capture net]]`.

## Route a conversational fix request through /fix

On a **board-enabled project**, when the operator raises a fix request in conversation — "can you fix X", a described bug, a reported regression — rather than naming an existing board item or issue number to resume, default to routing it through **`/fix`** (`claude/commands/fix.md`) instead of driving it ad hoc in the live session. `/fix` composes the existing state-probe → claim-first → isolated worker → PR → CI → modal-merge machinery, so the request gets the same claim-first board hygiene, PR verification surface, and issue-linkage discipline any other tracked fix gets — a fix driven by hand in conversation routinely skips one of those, most concretely a merged PR carrying no `Closes #N` and no board claim trail (§ Issue linkage, § Task workflow above). <!-- cite: K.44 class:unlinked-untracked-merge -->

This is a **strong default, not an absolute bar**: you may fix it directly in the live session only if you state up front — in the turn *before* editing — why the change is trivial enough to skip the `/fix` flow (the same bar § Plan-first default uses: a one-line fix, a typo, a comment, a mechanical config tweak), and the user doesn't object. Silence is not consent to skip; the rebuttal has to be voiced and given a beat to land. Absent that explicit, un-objected rebuttal, run `/fix <description>` (or `/fix <issue#>` when one already exists) rather than editing ad hoc.

**Why this exists.** A conversational fix that bypasses `/fix` skips claim-first board hygiene, the modal merge gate, and issue linkage in one motion — exactly the trace a merged-with-no-linkage PR, or an abandoned open PR with no issue reference, leaves behind. `claude/commands/tidy.md` § Unlinked fix PRs is this rule's backstop.

## Plan-first default

Default to **plan mode** before any non-trivial change. "Non-trivial" is broad: anything beyond a one-line fix, a typo, a comment, or a mechanical config tweak qualifies — new behavior, a multi-file edit, a new component, a schema touch, a refactor, a scorer/prompt/pipeline change. When in doubt, plan. (This is the plan-first habit the **Task workflow** section above composes with on board-enabled projects; here it applies generally, board or no board.) <!-- cite: K.45 class:opaque-classifier-reliance -->

This is a **strong default, not an absolute bar**: you may go straight to implementation only if you state up front — in the turn *before* editing — why the change is trivial enough to skip planning, and the user doesn't object. Silence is not consent to skip; the rebuttal has to be voiced and given a beat to land. Absent that explicit, un-objected rebuttal, enter plan mode, lay out the approach, and get approval before writing code.

**Why this exists.** The harness auto-classifier has caught implementation mistakes that planning would have surfaced first. That it caught them is the warning sign, not the safety net — it means our own controls were absent and we'd fallen back on a Claude built-in to backstop us. Built-in classifiers are opaque, can change without notice, and aren't ours to tune; leaning on them is leaning on luck. The plan-first default makes the control explicit and ours. If the auto-classifier ever fires on our work again, treat it as a process miss to investigate, not a catch to be grateful for.

Rationale: `[[Decisions/stageFind - Plan-first default for non-trivial changes]]`.

## Design-first default for invented work

Default to running **`/workshop`** before materializing invented, epic-sized work into a hand-authored epic. "Invented" means born in a conversation — an idea, a new capability, a "we should build X" — as opposed to *discovered* work (a Backlog defect, a sweep finding), which still enters through `/triage` as before; `/workshop` is the pipeline's **second front door**, for invented rather than discovered work (`[[Decisions/temperloop - design command as front door for invented work]]`). "Epic-sized" is the same threshold § Task workflow's "Decompose epic-sized work up front" rule already names (`{{EPIC_MIN_SUBUNITS}}`+ parallelizable sub-units, or more than one dependency level) — below it, a single board item is right and `/workshop`'s coverage walk is unneeded overhead. <!-- cite: K.46 incident:K#286 -->

This is a **strong default, not an absolute bar**: you may hand-author the epic directly only if you state up front — in the turn *before* creating it — why this invented work is trivial enough, or urgent enough, to skip the design walk, and the user doesn't object. Silence is not consent to skip; the rebuttal has to be voiced and given a beat to land. Absent that explicit, un-objected rebuttal, run `/workshop` first and let it materialize the epic (`claude/commands/workshop.md` Step 5) with its `## Contract` and `design-brief:` provenance marker.

**Why this exists.** A hand-authored epic skips the coverage walk's dimension checklist (`claude/design-schema.md`) — testability, uninstallability, adoption/enforcement, and the rest — exactly the gaps that surface expensively later (an unremovable feature, an untested seam, a design nobody can uninstall). `/assess`'s provenance check (`claude/commands/assess.md` Step 1) and the `/tidy` drain sweep (`claude/commands/tidy.md` Step 3 § Provenance-less epics) both backstop a hand-authored epic that skipped this default — but the backstop existing is not license to lean on it; it exists because the default sometimes has a legitimate exception (see above), not because skipping is fine. **Backstop scope — Contract-shaped epics only:** both nets key on a `## Contract` body, so an invented epic hand-decomposed straight into sub-issues with *no* Contract is invisible to both — a **ratified accepted-gap decision**, deliberately not widened here (flagging every Contract-less epic would drown the legitimate discovered-work epics `/triage` births): the temperloop#286 spike confirmed no reliable *retroactive* signal distinguishes a hand-authored invented epic from a `/triage`-born one, so a detection net over Contract-less epics has no basis that would not also drown the legitimate ones — see `[[Decisions/temperloop - provenance net scope (invented-epic distinguishability spike)]]` (accepted-gap record: temperloop#349).

Rationale: `[[Decisions/temperloop - design command as front door for invented work]]`.

## PR verification surface

Every PR must ship its own verification surface in the PR body — a way for the reviewer to confirm correctness without grepping logs, decoding JSON, or running commands themselves. A PR that asks the reviewer to "run the script and see" or "check the output file" is incomplete. The verification surface is part of the deliverable, not an optional add-on. This section is the by-change-type breakdown that `claude/message-schema.md`'s **PR-body skeleton** template (mode 6) defers to for its Verification surface slot — that template only requires the slot exist; this section owns its shape. <!-- cite: K.47 guard:workflows/scripts/build/pr.sh -->

What this looks like, by change type:

- **Script / behavior changes** (shell, board adapter, hooks, telemetry) — show the before/after of the observable behavior: the command's output before and after, the test that now passes, or the failure it now prevents. "Tests pass" alone is not a surface; show what the relevant test asserts.
- **Config / settings changes** (`settings.json`, permissions, dotfiles) — show the corrected value and the prior incorrect value side-by-side, plus what the change causes the harness to do differently. Don't make the reviewer diff two JSON blobs to find the one line that matters.
- **Doc / instruction changes** (`CLAUDE.md`, slash commands, skills, vault-facing rules) — quote the new or amended rule inline and name what it resolves or replaces. If it fixes a dangling reference or supersedes a prior rule, show the reference now resolving (the before/after of the pointer).
- **Refactors with no behavior change** — make an explicit "no behavior change" claim and show the diff or test that proves it (e.g. a shellcheck-clean run, a board-test pass, an idempotent `workflows/scripts/install-claude-md.sh` re-run — or `make install` in the foundation fleet).

When in doubt about what counts as adequate, err toward more visibility. The cost of an extra paragraph is small; the cost of a reviewer skipping verification because friction was too high is unbounded.

## Subagent usage

Exit plan mode before spawning an execution subagent (a `Task` call with a `subagent_type` that writes code, commits, or otherwise mutates state). Subagents inherit the parent session's plan-mode system-reminder — "MUST NOT make any edits... supersedes any other instructions" — and will stop after planning rather than executing. Plan mode is fine for read-only subagents (`Explore`, `python-reviewer`, `architecture-reviewer`, `requirements-auditor`) since they don't need write access anyway. <!-- cite: K.48 class:plan-mode-subagent-stall -->

This is documented Claude Code harness behavior, not a configurable setting. See [[Mistakes/foundation - Subagent harness stops + plan-mode re-activation]] for the root-cause analysis and the transcript evidence.

**Legible agent-gate degradation.** When an agent-gated step's reviewer is unavailable — per the capability-probe predicate ([[Decisions/foundation - Project capability probes]]: a review subagent is available iff the project declares it in `CLAUDE.md § Subagents` or `.claude/agents/`) — emit a one-line `skipped — <agent> unavailable` notice rather than silently no-opping — that **bare** wording is owned here and is the default form. **It has one sanctioned variant:** when the unavailable agent *ships as source* under `claude/agents/<agent>.md` but isn't installed, the line instead carries a remedy pointer — `skipped — <agent> available as source; run workflows/scripts/install/project-agents.sh to enable` — so an operator in a fresh clone sees the one-command fix on the live line rather than a bare dead-end. That remedy-bearing shape is defined in `claude/message-schema.md` § Degradation notice, which this rule points to rather than restates; the bare default stays kernel-owned as before. **The word `unavailable` is reserved for that capability-probe verdict and nothing else** — an agent that was declared, resolved and SPAWNED, and then failed to return inside a wall-clock ceiling, is a *timeout*, and its notice says `timed out after <actual>s` instead, naming the wall clock actually waited. Conflating the two is not a wording nit: temperloop#2064's §3e timer collapsed a 1200s review ceiling to ~41s real and reported every discarded reviewer `unavailable`, which sent the next investigator at the agent roster — where nothing was wrong — instead of at the timer. A silent skip is the foundation #164 failure: the gate looks like it passed when it never ran. `/triage` Step 3 and `/assess` Step 3 already do this; the PR-review / Decisions-lock advisory and `build` 3e must too. <!-- cite: K.49 incident:F#164 -->

**Cost-tier routing — the cheapest tier that fits the stage, set explicitly.** Two levers, one principle (spend judgment-tier compute only where the judgment is needed): <!-- cite: K.50 class:default-to-strongest-cost-leak -->

- **Delegate to a subagent** any high-volume or context-polluting work — a broad grep sweep, a log trawl, a many-file read — rather than running it in the driver's own context; keep only the findings back in the parent (this is the same reasoning `/build`'s worker isolation already applies, generalized to any noisy investigation).
- **Set a worker or fan-out agent's model tier *explicitly* to the cheapest tier that fits the work's judgment level**, rather than defaulting every agent to whatever tier the driver runs. Mechanical, high-volume, or low-judgment stages route to the cheaper tier; genuinely high-judgment stages (a merge decision, an architectural fork) route to the stronger tier. **Which** model each tier maps to is a setting, never a literal in this prose (§ Named-setting convention): the autonomous pipeline driver's two model settings — `PIPELINE_DRIVE_MODEL` (mechanical drives) and `PIPELINE_DRIVE_MERGE_MODEL` (high-judgment code/merge drives) in `workflows/scripts/build/build.config.sh` — are the worked example, and a new fan-out site names its own model setting the same way. The failure this prevents is a fan-out that silently launches many agents on the top tier for work that never needed it — the default-to-strongest cost leak an explicit, config-named tier closes.
- **Every headless spawn passes an explicit `--model` — a bare `claude -p` / `--print` is never acceptable.** A `claude -p` with no `--model` does not inherit the launching session's model: it resolves the machine's saved default model, so a fan-out script composed mid-run silently routes every worker to whatever tier that host was last configured for — the tier set above is chosen and then thrown away. This binds any headless spawn, including a throwaway script written into `/tmp`, and the flag's value is named from a setting per the bullet above, never a hard-coded model id. `workflows/scripts/validate-model-usage-emit.sh` (§ 6e) is the mechanical half for spawn sites that live in the repo; the run-time-composed case is backstopped by the `claude-p-spawn-guard.sh` PreToolUse hook (`claude/hooks/`), which scans a Bash command's whole text — heredoc bodies included, so it fires on the heredoc that *authors* a `/tmp` fan-out script — and asks before a bare spawn. Neither reaches a bare spawn inside an already-committed script invoked by path, one behind a launcher prefix the hook does not list, or one launched outside the harness: that residue is carried by this rule alone.
